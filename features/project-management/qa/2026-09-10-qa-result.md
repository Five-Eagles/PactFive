## 왜 시드 계정 대신 mock 인증으로 했나

처음에는 `.env` 가 없어 `seed:dev-accounts` 를 못 돌렸다. 이후 받은 env 파일에도
**`DATABASE_URL` 이 없다** — 2026-09-10 부터 시드 스크립트가 로컬 `users` 행을 Prisma 로
직접 넣기 때문에 이 값이 꼭 필요하다(`scripts/seed-dev-accounts.md`).

`DATABASE_URL` 없이 돌리면 Supabase 쪽 계정만 만들어지고 로컬 `users` 행은 빠진 채로 남는다.
공용 Supabase 에 반쪽짜리 계정을 남기지 않으려고 **시드는 돌리지 않았다.**

**대신 mock 인증으로 상태를 직접 만들어 확인했다.** 결과적으로 이쪽이 증거로 더 낫다 —
시드 계정은 여러 상태가 섞여 있어 "무엇 때문에 이 응답이 나왔는지"가 흐려지는데,
직접 만들면 규칙 하나만 떼어 볼 수 있다.

`client-recruitment-closed` 계정이 필요한 시나리오(마감된 프로젝트)도
`close-recruitment` 를 직접 호출해 같은 상태를 만들었다.

## 1. 회의 자료와 실제가 다른 것 — 2건

### ① 북마크 중복은 409 가 아니라 200 이다

**회의 자료 6번:** *"같은 프로젝트를 다시 북마크 추가 → 409(중복)"*

**실제:**

| 회차 | HTTP | `changed` | `bookmarkedAt` |
|---|---|---|---|
| 1 | 200 | `true` | 05:29:59.215 |
| 2 | 200 | **`false`** | 05:29:59.215 |
| 3 | 200 | **`false`** | 05:29:59.215 |

목록에는 1건만 들어간다. 중복 저장은 안 된다.

**왜 오류가 아닌가.** `bookmark.service.ts` 에 명시돼 있다 —

> 이미 있다. **오류가 아니다** (규칙 1).
> 미리 조회해서 막지 않고 여기서 잡는 이유: 조회와 삽입 사이의 틈을 없앨 수 없다.
> 더블클릭한 두 요청이 둘 다 조회를 통과한 뒤 둘 다 삽입을 시도한다.

**저장 시각이 안 바뀌는 것도 규칙이다** (규칙 3). 다시 누를 때마다 갱신되면
"최근 저장순" 목록에서 순서가 튄다.

**QA 기준을 이렇게 바꿔야 한다:** 409 가 아니라 **`changed: false`** 를 본다.
409 가 나오면 그게 버그다.

### ② 마감일 수정 시나리오는 그대로는 422 에 도달하지 못한다

**회의 자료 2·3번:** `client-recruiting` 프로젝트의 마감일을 수정해 422 확인

**실제:** 그 프로젝트에는 이미 지원자가 있어 **409 로 먼저 막힌다.**

```
상태  409
코드  PROJECT_EDIT_LOCKED
문구  "지원자가 있어 예산과 일정은 변경할 수 없습니다."
상세  lockedFields: ["recruitmentDeadlineAt"]
      pendingApplicationCount: 1
```

**왜 그런가.** `updateProject` 의 검증 순서가 이렇다 (`project.service.ts` 505~518행).

```
1. 잠금 검사(규칙 15)   → 409 PROJECT_EDIT_LOCKED   ← 여기서 멈춘다
2. 마감일 검사           → 422 ...                    ← 도달하지 않는다
```

시드 스크립트가 `freelancer-applicant` 의 지원을 그 프로젝트에 붙여 둔다
(`scripts/seed-dev-accounts.js:578`).

**그래서 둘로 나눠서 했다** — 잠금 확인은 그대로, 경계값은 지원자 없는 새 프로젝트로.
둘 다 유효한 QA 항목이고 오히려 규칙 15 확인이 하나 늘었다.

## 2. 확인한 것 전부 (API)

### 잠금 규칙 (규칙 15)

| 확인 | 결과 |
|---|---|
| 지원자 있는 프로젝트의 마감일 수정 | **409 `PROJECT_EDIT_LOCKED`** |
| 응답에 `lockedFields` 포함 | `["recruitmentDeadlineAt"]` |
| 응답에 `pendingApplicationCount` 포함 | `1` |

`pendingApplicationCount` 가 **1 로 제대로 세어진다** — CR-AP-001 로 연 갱신 통로가
실제로 도는 증거다.

### 마감일 경계값

지원자 0명인 새 프로젝트로 확인했다.

| 넣은 값 | HTTP | 코드 |
|---|---|---|
| 현재 +12시간 | 422 | `DEADLINE_BELOW_MINIMUM` |
| 현재 +400일 | 422 | `DEADLINE_EXCEEDS_LIMIT` |
| 어제 | 422 | `DEADLINE_MUST_BE_FUTURE` |
| **정확히 +1일** | **200** | 통과 |
| **정확히 +365일** | **200** | 통과 |

**막히는 쪽만 보지 않고 경계 안쪽도 찍었다.** 통과해야 할 값까지 막는 버그는
거부 케이스만 봐서는 못 잡는다.

회의 자료에 없던 것 둘을 추가로 확인했다 — `DEADLINE_MUST_BE_FUTURE`(과거 날짜)와
정확한 오류 코드 `DEADLINE_EXCEEDS_LIMIT`(자료에는 "422, 최대 365일 초과 오류"로만 적혀 있었다).

### 마감 처리 (규칙 22·23)

| 확인 | 결과 |
|---|---|
| 지원자 1명 있는 프로젝트 마감 | 200 · `CLOSED` |
| 대기 지원 자동 거절 | `rejectedApplicationCount: 1` |
| **마감 후 `pendingApplicationCount`** | **0** |
| `applicationCount`(누적) | **1 로 유지** — 내려가지 않는다 |
| 수정 가능 항목 | `[]` — 전부 잠김 |
| 가능한 행동 | `CANCEL` · `DELETE` · `REOPEN_RECRUITMENT` |
| 공개 목록에서 제외 (규칙 10) | 2건 → 1건 |

**대기 수 0 처리도 실제로 돈다** — CR-AP-001 에서 "하나씩 빼지 않고 0 으로 놓는다"고
한 그 동작이다.

### 북마크 (규칙 1·3·7·13)

| 확인 | 결과 |
|---|---|
| 추가 | 200 · `changed: true` |
| 중복 추가 2회 | 200 · `changed: false` · 시각 유지 |
| 목록 건수 | 1건 (중복 저장 안 됨) |
| **마감된 프로젝트 북마크** | **200** — 저장된다 (규칙 7) |
| **마감돼도 내 목록에 남나** | **남는다** (규칙 13) |

마지막 둘은 회의 자료에 없던 항목이다. engagement 의 핵심 규칙이라 같이 확인했다 —
"지원할 수 없게 된 것도 담아 둔 것은 그대로 보인다"가 이 기능의 약속이다.

## 3. 아직 확인하지 못한 것

**실제 시드 계정으로의 QA.** 받은 env 파일에 `DATABASE_URL` 이 없어 못 했다.
화면 QA(5절)는 같은 상태를 mock 인증으로 만들어 끝냈으므로, 남은 것은
"시드 계정으로 로그인해도 같은 화면이 나오는가" 한 가지다.

`DATABASE_URL` 을 받으면 다음 순서로 이어서 한다.

```
1. seed:dev-accounts 실행
2. client-recruiting 로그인 → 내 프로젝트에 RECRUITING 1건
3. client-recruitment-closed 로그인 → 마감 화면 문구
4. freelancer-fresh 로그인 → 북마크 화면 반응
```

**`client-recruitment-closed` 계정은 `INTERNAL_SERVICE_TOKEN` 이 있어야 만들어진다**
(Action Item ④). 시드 스크립트가 `/internal/v1/projects/sweep-deadlines` 를 호출해
실제로 CLOSED 까지 밀어붙이는 구조다 — 그 엔드포인트는 2026-09-09 에 열었다(PR #98).
토큰이 없으면 오류 없이 **조용히 건너뛴다.** 받은 env 파일에는 이 토큰이 들어 있다.

## 5. 화면 QA

API 에서 확인한 상태(잠긴 프로젝트 · 지원자 없는 프로젝트 · 마감된 프로젝트)를 그대로
화면에서 다시 봤다. 의뢰인·프리랜서 두 역할로 로그인해 확인했다.

### 규칙대로 보인 것

| 화면 | 확인 | 결과 |
|---|---|---|
| 프로젝트 수정 (잠김) | 안내 문구 | "지원자 1명이 있어 예산과 일정은 변경할 수 없습니다." · 예산·일정 입력칸 읽기 전용 |
| 프로젝트 수정 (새 프로젝트) | 마감일 오늘 | "마감 일시는 최소 1일 뒤여야 합니다." |
| | 마감일 +400일 | "모집 기간은 최대 365일입니다." |
| | 마감일 어제 | "마감 일시는 현재 시각보다 뒤여야 합니다." |
| | 저장된 값 | 세 경우 모두 422 · 마감일 그대로 |
| 내 프로젝트 | 버튼 활성 여부 | 서버가 준 가능한 행동과 일치 |
| 북마크 버튼 | 저장 ↔ 해제 | 경고창 없이 전환 |
| 내 북마크 | 마감된 프로젝트 | 목록에 남고 "모집이 마감되었습니다" 표시 |

**화면에서 "+12시간"은 "오늘 날짜"와 같다.** 수정 화면의 마감일 칸은 날짜만 고르는 칸이고
그날 23:59:59 로 저장된다(`shared/date.ts`). 그래서 화면 QA 에서는 오늘 날짜를 골랐다.

### 고친 것 — 5건

모두 project-management 화면 코드 안에서 고쳤다. 서버 규칙은 건드리지 않았다.

| # | 화면 | 전 | 후 | 이유 |
|---|---|---|---|---|
| 1 | 내 프로젝트 요약 | 지원 **0**건 (마감된 프로젝트) | 지원 **1**건 | 대기 중 지원 수를 쓰고 있었다. 마감하면 대기 수는 0 이 되므로 "한 명도 지원 안 함"으로 읽혔다. 상세 화면처럼 누적 지원 수로 맞췄다 |
| 2 | 내 프로젝트 요약 | "협상이 끝났으나 마감일이 지났습니다" | "모집을 마감했습니다" | 재모집 가능 여부만 보고 문구를 골라, 협상한 적 없는 프로젝트에도 이 문구가 붙었다. 마감일이 지났는지로 "마감일이 지났습니다" / "모집을 마감했습니다"를 가른다 |
| 3 | 프로젝트 상세 머리 | 배지 "모집 마감" 옆에 "마감 15일 전" | "모집 마감" | 일찍 마감하면 마감일이 아직 미래라 남은 날수가 계속 보였다 |
| 4 | 프로젝트 상세 의뢰인 | "평점 0 · 리뷰 0건" | "평가 없음 · 리뷰 0건" | 0 점은 "나쁘다"로 읽힌다. 아직 평가가 없다는 뜻이 맞다 |
| 5 | 프로젝트 상세 (마감) | "지원서는 의뢰인에게 바로 전달됩니다" | 표시 안 함 | 지원 버튼이 막혀 있는데 지원 안내가 남아 있었다 |

고친 뒤 같은 상태로 다시 확인했다 — 타입 검사 · `npm run check:design` 통과.

### 참고 — 고치지 않은 것

- **의뢰인 이름이 "알 수 없음"으로 보인다.** mock 계정에 프로필이 없어서다. 시드 계정에는
  프로필이 있으므로 3절의 시드 QA 에서 다시 본다.
- **공개 목록 카드의 마감 표시는 그대로 뒀다.** 마감된 프로젝트는 공개 목록에서 빠지므로
  (규칙 10) 3번과 같은 어긋남이 카드에서는 생기지 않는다.
