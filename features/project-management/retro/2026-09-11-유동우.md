## 잘한 점 (Keep)

**규칙을 글로 먼저 정하고 코드를 썼다.**
QA 때 회의 자료의 기대값과 실제 동작이 두 군데 달랐는데, 둘 다 규칙 문서에 이유가 적혀 있어서
"버그가 아니라 기대값이 틀렸다"고 바로 설명할 수 있었다.

**남의 영역은 직접 고치지 않고 변경 요청으로 넘겼다.**
공용 설계 문서나 다른 기능 코드가 바뀌어야 할 때마다 요청서로 정리했다. 다섯 명이 같은 저장소를
쓰는데도 서로의 작업을 덮어쓰는 일이 없었다.

**QA에서 막히는 경우만이 아니라 통과해야 하는 경우도 확인했다.**
"1일 뒤"·"365일 뒤"처럼 경계에 딱 걸리는 값이 통과하는지까지 봤다. 거부만 확인하면 통과해야 할
값까지 막는 버그를 놓친다.

## 아쉬운 점 (Problem)

**코드를 다 읽기 전에 설계를 답해서 정정이 반복됐다.**
다른 기능과 맞닿는 부분을 정리할 때 일부만 보고 답했다가 몇 번 고쳐 말해야 했다.
결국 전체를 다시 조사하고 나서야 정리가 끝났다.

**방문자에게 보이는 화면에 내부용 안내를 넣었다.**
준비 중 화면에 담당자와 파일 위치를 적었다. 개발 중 확인용이었지만, 실제 서비스라고 생각하면
방문자가 볼 이유가 없는 정보였다.

**서버 규칙은 맞았는데 화면 문구가 상태를 다 따라가지 못했다.**
마감된 프로젝트에 "마감 15일 전"이 같이 보이거나, 리뷰가 없는 의뢰인이 "평점 0"으로 보이는 등
QA에서 5건이 나왔다. 상태 조합별로 어떤 문구가 나와야 하는지 미리 정해 두지 않았다.

**기능 사이 연결의 주인을 늦게 정했다.**
지원 건수를 누가 올리고 누가 내리는지 초반에 정하지 않아, 개발 후반에야 정리했다.

**QA 준비물을 늦게 확인했다.**
실제 계정 QA에 필요한 설정값이 빠진 것을 QA 당일에 알아서 하루가 밀렸다.

## 다음에 해볼 점 (Try)

1. 설계를 답하기 전에 관련 코드를 끝까지 읽는다.
2. 화면 문구는 "실제 사용자가 본다"를 기준으로 쓰고, 내부 정보는 코드 주석에만 남긴다.
3. 시안을 만들 때 상태별 문구 표를 같이 만든다 — 모집 상태 × 거래 상태 조합마다 무엇이 보이는지.
4. 기능 사이 연결은 시작할 때 "누가 쓰고 누가 읽는지"부터 합의한다.
5. QA 전날 설정값·계정 같은 준비물을 먼저 점검한다.
