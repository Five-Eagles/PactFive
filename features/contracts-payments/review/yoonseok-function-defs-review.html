1. startProjectTransaction

반드시 확정: 호출 주체, 수락된 지원 ID, 프로젝트 시작 상태

최윤석은 이 함수를 구현·호출하지 않습니다. 수락된 지원 ID가 프로젝트에 심긴 뒤에만 조준영이 계약 흐름에 들어갑니다.

항목현재 초안
호출 주체조준영 → 유동우. 최윤석은 호출하지 않음
수락된 지원 IDC-01이 accepted_application_id에 기록. start 요청에 applicationId를 다시 실지 않음
시작 상태수락 직후 CLOSED + CONTRACT_PENDING. 이후 서명·결제 후 IN_PROGRESS
순서accept 성공 → 나머지 거절 → 알림. 그 다음 금액합의/start
#질문예아니오대안
A1accept 성공 → 나머지 거절 → 알림 후에야 조준영이 계약 흐름에 들어가는가
A2C-01이 acceptedApplicationId를 심는 것으로 충분하고 start에 applicationId를 다시 안 실어도 되는가
A3수락 전 acceptedApplicationId가 null이면 조준영이 계약 흐름을 시작하지 않는다고 가정해도 되는가
A4한 프로젝트의 수락 지원은 최대 1건인가

2. restorePreContractProject

반드시 확정: 복원 대상 상태, 합의·계약 취소와의 관계 (지원에 닿는 부분)

항목현재 초안
복원 대상거래 NONE. 조건부 모집 OPEN. 거절된 지원을 되살리지 않음
합의·계약조준영 테이블. restore는 프로젝트만. 대기 지원이 남으면 rejectPendingApplications 재요청
대기 지원 잔존200, reopened false, notReopenedReason PENDING_APPLICATIONS_REMAIN
재개 성공새 지원은 기존 PENDING 규칙
#질문예아니오대안
B1restore가 자동 거절된 지원자를 되살리지 않는 전제를 Mock이 지키는가
B2PENDING_APPLICATIONS_REMAIN일 때 rejectPendingApplications 재요청을 다시 받을 수 있는가
B3재개된 프로젝트의 새 지원은 기존 PENDING 규칙인가
B4프로젝트 취소와 합의 최종 거절을 지원 거절 사유에서 구분하는가

기존 확인 3문항

#질문예아니오메모
1accept 성공 → 나머지 거절 → 알림 후에 start 흐름 (A1과 같음)
2restore 중 rejectPendingApplications 재요청 수신 (B2와 같음)
3재개 후 새 지원 = 기존 PENDING (B3와 같음)

결제·완료 함수는 유동우 문서에서만 다룹니다.
