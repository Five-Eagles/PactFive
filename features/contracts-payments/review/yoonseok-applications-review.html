지원 수락 이후 계약 흐름 확인 요청

수신: 최윤석 (applications · notifications) · 발신: 조준영 (contracts-payments) · 2026-08-25
출처: features/contracts-payments/spec.md 규칙 3 · 5 · 7 · 정본 PRD v6.4 §5.4 C-01 호출 순서 · D-43
작업 가설 합의되면 spec·API 계약을 확정본으로 올린다.

이 문서는 applications Mock이 계약 흐름과 맞물리는 지점만 확인하기 위한 것이다. 결제·완료 REST(markPaymentPending, completeProjectTransaction)는 넣지 않았다. 조준영이 유동우에게 부르는 출발점은 startProjectTransaction이며, 그 선행이 최윤석의 지원 수락이다.

확인 체크리스트

해당 칸에 표시하고, 다르면 메모에 대안을 적어 주세요.

#확인 항목예아니오메모
1 acceptProjectApplication 성공 → 나머지 지원 거절 → 알림 순서가 끝난 뒤에야 조준영이 startProjectTransaction 흐름(금액합의·서명)에 들어가는 것을 applications Mock에 반영하는가. (PRD §0.2 #6)
2 restorePreContractProject 중 유동우가 rejectPendingApplications를 재요청하면 applications Mock이 다시 받을 수 있는가. (D-43 · 일괄 거절 부분 실패로 대기 지원이 남은 경우)
3 합의 최종 거절 후 재개된 프로젝트(reopened: true, 모집 OPEN)의 새 지원은 기존과 같은 PENDING 규칙인가.

왜 startProjectTransaction이 최윤석과 연결되는가

startProjectTransaction은 조준영 → 유동우 호출이다. 그러나 실행 전 상태는 반드시 CONTRACT_PENDING이어야 하고, 그 상태로 만드는 함수가 최윤석의 acceptProjectApplication이다. 수락이 끝나기 전에 조준영이 금액합의·서명을 시작하면 프로젝트 상태가 아직 NONE이라 이후 start가 409가 된다.

PRD가 정한 수락 순서: ① acceptProjectApplication 성공 → ② 나머지 지원 거절 → ③ 알림. 이 세 단계가 Mock에서 끝난 뒤에만 조준영 흐름이 시작된다고 가정한다.

해피패스 호출 순서 (spec 규칙 7)

  1. 최윤석 acceptProjectApplication 성공 → recruitmentStatus: CLOSED, transactionStatus: CONTRACT_PENDING
  2. 최윤석 나머지 대기 지원 거절 + 알림
  3. 조준영 금액합의 · 계약 서명
  4. 조준영 markPaymentPending → PG → SIGNED ∧ PAID
  5. 조준영 startProjectTransaction → IN_PROGRESS
  6. 작업 · 납품 APPROVED ∧ 정산 RELEASED → completeProjectTransaction

최종 거절 시에만 조준영이 restorePreContractProject를 부른다. 재제안·제안 철회·프로젝트 취소 때는 부르지 않는다.

startProjectTransaction 요약 (최윤석이 알면 되는 범위)

항목내용
호출조준영 → 유동우. 최윤석은 이 함수를 직접 부르지 않는다.
선행 상태최윤석 수락으로 만든 CONTRACT_PENDING
호출 조건계약 SIGNED 그리고 결제 PAID (둘 다)
실행 후IN_PROGRESS. 모집은 CLOSED 유지.
최윤석 영향이 시점 이후 새 지원은 받지 않는다 (이미 마감).

restorePreContractProject와 지원 도메인 (D-43)

조준영이 최신 제안의 최종 거절 때 유동우에게 복원을 요청한다. 유동우가 projects만 되돌리고, 이미 자동 거절된 지원자는 복구하지 않는다.

조건프로젝트 결과최윤석에게
마감일 남음 + 대기 지원 0건 OPEN + reopened: true + transactionStatus: NONE 새 지원을 기존 PENDING 규칙으로 받을 수 있음 (체크리스트 3)
마감일 지남 + 대기 지원 0건 CLOSED + reopened: false 재모집은 의뢰인 확인 화면. 당장 새 지원 없음
대기 지원이 남아 있음 (수락 시 일괄 거절 부분 실패) CLOSED + reopened: false + HTTP 200 (OPEN 보류) 유동우가 rejectPendingApplications를 재요청. Mock이 이 두 번째 호출을 받아야 함 (체크리스트 2)

같은 negotiationId로 restore가 다시 오면 유동우는 최초 결과를 그대로 돌려준다. 그 사이에 새 지원자가 수락된 뒤 지연된 이전 restore가 도착하면 409 PROJECT_ALREADY_RESTORED로 거부되어 새 계약 대기가 유지된다 (PM-55).

{ "projectId": "prj_123", "negotiationId": "ngt_123",
  "recruitmentStatus": "OPEN", "transactionStatus": "NONE",
  "reopened": true,
  "restoredFields": ["recruitmentStatus", "transactionStatus"],
  "alreadyProcessed": false, "projectVersion": 8 }

위는 재개 성공 예시이다. 대기 지원 잔존이면 recruitmentStatus: "CLOSED", reopened: false.

하지 않는 일

  • 조준영/유동우가 applications 테이블을 직접 UPDATE하지 않는다.
  • restore가 이미 자동 거절된 지원자를 되살리지 않는다.
  • 최윤석이 startProjectTransaction을 구현하거나 호출하지 않는다.
