함수별 필수 정의 확인 회신 — 최윤석

수신: 조준영 (contracts-payments) · 회신: 최윤석 (applications · notifications) · 2026-08-26
검토 기준: PRD v6.4 §5.4 · ERD v1.4 · features/contracts-payments/spec.md · 전달받은 start / restore 확인 문서

검토 결과
전달받은 현재 초안의 호출 순서와 applications 경계에 동의합니다. A1~A4, B1~B4 및 기존 확인 1~3까지 총 11개 항목을 모두 “예”로 확인합니다.

1. startProjectTransaction 연계 확인

startProjectTransaction 자체는 최윤석 담당 함수가 아니며, applications에서는 계약 흐름 진입 전에 필요한 지원 수락 상태와 호출 순서만 보장하는 것으로 확인합니다.

acceptProjectApplication 성공 → 나머지 PENDING 지원 거절 → 알림 처리 → 계약·금액합의 흐름 진입
# 확인 항목 답변 검토 메모
A1 acceptProjectApplication 성공 → 나머지 지원 거절 → 알림 완료 후 계약 흐름으로 진입하는가 ✓예 수락 처리와 후속 거절·알림이 먼저 완료된 뒤 계약 단계로 넘어가는 순서로 반영합니다.
A2 C-01에서 acceptedApplicationId를 기록하면 start 요청에 applicationId를 다시 전달하지 않아도 되는가 ✓예 프로젝트에 기록된 acceptedApplicationId를 기준으로 연결하며, start 요청에서 중복 전달하지 않는 구조에 동의합니다.
A3 수락 전 acceptedApplicationId = null 상태에서는 계약 흐름을 시작하지 않는다고 가정해도 되는가 ✓예 수락된 지원자가 확정되지 않은 상태에서는 계약 선행조건이 충족되지 않은 것으로 봅니다.
A4 한 프로젝트의 최종 수락 지원은 최대 1건인가 ✓예 프로젝트당 acceptedApplicationId는 1건만 유지하는 기준으로 정리합니다.

2. restorePreContractProject 연계 확인

restore는 프로젝트 상태 복원에 해당하며, applications에서는 기존 자동 거절 지원자의 상태 유지, 남은 PENDING 처리, 재개 후 신규 지원 규칙을 보장하는 것으로 확인합니다.

# 확인 항목 답변 검토 메모
B1 restore가 이미 자동 거절된 지원자를 다시 되살리지 않는 전제를 applications Mock이 유지하는가 ✓예 기존 REJECTED 지원은 그대로 유지하며, 프로젝트 재개만으로 이전 지원 상태를 복구하지 않습니다.
B2 PENDING_APPLICATIONS_REMAIN 발생 시 rejectPendingApplications 재요청을 다시 받을 수 있는가 ✓예 일괄 거절의 부분 실패 등으로 PENDING이 남은 경우, 동일 목적의 재요청을 applications 측에서 다시 처리할 수 있도록 합니다.
B3 재개된 프로젝트(reopened: true, 모집 OPEN)의 새 지원은 기존과 같은 PENDING 규칙인가 ✓예 재모집 이후 들어오는 신규 지원은 기존 지원 생성 규칙과 동일하게 PENDING으로 처리합니다.
B4 프로젝트 취소와 합의 최종 거절을 지원 거절 사유에서 구분하는가 (PROJECT_CANCELED vs AGREEMENT_DECLINED 등) ✓예 프로젝트 자체 취소와 계약·합의 결렬은 발생 원인이 다르므로 applications에서도 별도 거절 사유로 구분하는 기준에 동의합니다.

3. 기존 확인 3문항

원본 문서의 기존 확인 항목은 A1, B2, B3와 동일한 내용으로 확인되며, 중복 여부와 관계없이 회신 형식상 각각 별도로 답변합니다.

# 확인 항목 답변 검토 메모
1 accept 성공 → 나머지 거절 → 알림 후에 start 흐름으로 진입하는가 ✓예 A1과 동일하게 확인합니다.
2 restore 중 rejectPendingApplications 재요청을 applications Mock이 다시 받을 수 있는가 ✓예 B2와 동일하게 확인합니다.
3 재개 후 새 지원은 기존과 동일한 PENDING 규칙을 적용하는가 ✓예 B3와 동일하게 확인합니다.

4. 최종 정리

총 11개 확인 항목 전체를 “예”로 회신합니다.
applications 측은 수락 → 잔여 지원 거절 → 알림 → 계약 진입 순서를 유지하고, restore 시에는 기존 거절 지원을 복구하지 않으며, 재개 프로젝트의 신규 지원은 기존과 동일한 PENDING 규칙으로 처리하는 방향에 동의합니다.

※ markPaymentPending, completeProjectTransaction, startProjectTransaction의 직접 구현·호출은 applications 담당 범위에서 제외합니다.
