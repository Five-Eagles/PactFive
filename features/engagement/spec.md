# engagement — SPEC

## 목적

프리랜서가 프로젝트를 **담아두고 발견하도록** 돕는다. 북마크 저장·해제·목록과, 프로젝트 상세 하단의 추천 프로젝트가 이 기능의 전부다.

## 범위

- **포함**: 북마크 추가·제거(토글) · 내 북마크 목록 · 추천 프로젝트 계산
- **제외**: 프로젝트의 생성·수정·상태 변경 일체(`features/project-management/`) · 지원서(최윤석) · 마감 임박 알림(최윤석, B3-2 백로그)

## 담당 경계 — 이 기능의 전제

**engagement는 프로젝트를 읽기만 한다.** 어떤 경로로도 쓰지 않는다.

`project-management`와 담당자가 같지만 경계는 그대로 지킨다. 섞으면 "북마크를 눌렀더니 프로젝트 상태가 바뀌는" 결함이 생길 수 있고, 나중에 떼어내기도 어려워진다.

## 관련 엔티티 (근거: `docs/domain/erd.md`)

### `bookmarks`

`id` · `freelancer_id` · `project_id` · `created_at`

**이 기능이 쓰는 테이블은 이것 하나다.**

### 읽기만 하는 것

`projects`(유동우 · project-management) — 존재 여부 · `deleted_at` · `recruitment_status` · `category` · `created_at`, 그리고 카드 표시 필드.
`project_skills`(유동우) — 추천 우선순위의 기술 겹침 판정.
`users`(오민혁) — 프리랜서 역할 확인.

### 만들지 않는 테이블

`recommendations` 를 **만들지 않는다.** 추천 결과를 캐시나 별도 저장소에 쌓지 않는다.

프로젝트 상태는 시간에 따라 바뀐다(모집 중 → 마감). 저장해두면 이미 마감된 프로젝트를 계속 추천하게 되고, 그걸 막으려면 동기화 로직이 또 필요해진다.

## 상태 모델

북마크에는 상태 컬럼이 없다. **행이 있으면 저장됨, 없으면 해제됨**이다.

```text
해제됨  --(추가)-->  저장됨
저장됨  --(제거)-->  해제됨
저장됨  --(추가)-->  저장됨    변화 없음
해제됨  --(제거)-->  해제됨    변화 없음
```

같은 프리랜서가 같은 프로젝트를 두 번 저장할 수 없다.

## 규칙

### 북마크 토글

1. **"추가"는 "1건 만든다"가 아니라 "1건 있는 상태로 만든다"이다.** 이미 있으면 새로 만들지 않고 성공으로 응답한다.
2. **"제거"는 "1건 지운다"가 아니라 "0건인 상태로 만든다"이다.** 이미 없어도 오류가 아니고 성공으로 응답한다.
3. 이미 저장된 것을 다시 추가해도 **`created_at`을 갱신하지 않는다.** 갱신하면 "최근 저장순" 정렬에서 순서가 튄다.
4. 북마크 제거는 **행을 실제로 지운다.** 프로젝트와 달리 소프트 삭제하지 않는다. 거래 이력이 아니고, 사용자는 "지웠는데 남아 있는" 것을 원하지 않는다.
5. 프리랜서만 북마크를 추가·제거할 수 있다. 비로그인은 `401`, 의뢰인은 `403`.
6. 없거나 삭제된 프로젝트는 북마크할 수 없다 → `404`. 판정은 project-management가 제공하는 조회를 거치고, `projects` 컬럼을 직접 읽지 않는다.
7. **모집 마감·거래 진행·취소된 프로젝트도 북마크할 수 있다.** 프리랜서가 "이런 조건의 프로젝트가 있었지"를 참고하려고 담아두는 경우가 있다.
8. 이미 저장한 프로젝트가 마감·취소돼도 **북마크를 자동으로 지우지 않는다.** 의도하지 않은 데이터 소실이 된다.

### 내 북마크 목록

9. **로그인한 본인이 저장한 것만** 나온다. 남의 북마크 목록은 어떤 방법으로도 볼 수 없다 → 다른 사람 것을 요청하면 `403`.
10. 기본 정렬은 **최근에 저장한 것부터**다. 프로젝트 등록순이 아니라 북마크 저장순이다.
11. 페이지당 10개다.
12. **삭제된 프로젝트는 목록에서 빠진다.** 북마크 데이터 자체는 남긴다 — 프로젝트가 되살아날 일은 없지만, 지우는 쪽이 더 위험하다.
13. **마감된 프로젝트는 목록에 남는다.** 공개 목록(project-management 규칙 10)과 반대다. 공개 목록은 "찾는 곳"이라 지원 가능한 것만 보여주고, 내 북마크는 "내가 담아둔 것"이라 내가 지우기 전엔 남는다.
14. 마감된 항목은 카드를 정상 표시하되 **지원하기를 비활성**한다. 상세 보기와 북마크 해제는 계속 가능하다.
15. 목록이 비어 있는 것은 오류가 아니다. 빈 상태 안내와 "프로젝트 둘러보기"를 함께 내려보낸다.

### 추천 프로젝트

16. 프로젝트 상세 화면 **하단**에 붙는 보조 섹션이다. 로그인 없이도 볼 수 있다.
17. 요청이 올 때마다 **그 시점의 프로젝트 데이터로 계산한다.** 저장하지 않는다.
18. 후보는 세 조건을 **전부** 만족해야 한다 — 삭제되지 않았다 · 모집 상태가 `OPEN`이다 · 지금 보고 있는 프로젝트가 아니다.
19. 모집 예정과 마감은 추천하지 않는다. 추천의 목적이 "지금 지원할 수 있는 것을 발견하는 것"이기 때문이다.
20. 우선순위는 세 단계다. 1순위 **카테고리가 같고 그리고 기술이 하나 이상 겹침**, 2순위 카테고리만 같음, 3순위 기술만 겹침.
21. 같은 순위 안에서는 **최근에 등록된 것부터**다.
22. **4건 고정**이다. 파라미터로 조정할 수 있게 만들지 않는다.
23. 4건보다 적으면 **있는 만큼만** 준다. 채우려고 조건을 완화하지 않는다.
24. 후보가 하나도 없어도 오류가 아니다. 빈 목록을 정상 응답으로 주고 **화면은 섹션 자체를 감춘다.**
25. 없거나 삭제된 프로젝트의 추천을 요청하면 `404`.
26. **점수 기반 랭킹 · 벡터 검색 · 개인화 · 머신러닝 · 협업 필터링을 하지 않는다.** RFP가 명시적으로 범위 밖에 둔다.

### 응답에 없어야 하는 것

27. 북마크 목록과 추천 응답 어디에도 **`transactionStatus` 키를 넣지 않는다.** `null`로도 내려보내지 않는다. 이 기능의 사용자는 프리랜서이고, 거래 상태는 등록 의뢰인만 본다.
28. 추천 응답에 **내부 점수나 순위값을 넣지 않는다.** 순위는 정렬 순서로만 표현한다. 값을 내보내면 화면이 그것으로 다시 정렬하려 들고, 나중에 계산 방식을 바꿀 수 없게 된다.
29. 어떤 응답에도 `deletedAt`을 넣지 않는다.

### 화면에서 지키는 것

30. 북마크 아이콘은 보는 사람에 따라 다르다 — 비로그인은 **표시하되 누르면 로그인 유도**, 프리랜서는 저장/해제 상태 반영, 의뢰인은 **표시하지 않는다.**
31. 아이콘을 먼저 바꾸고 요청을 보내는 방식(낙관적 반영)을 쓴다면, **실패했을 때 반드시 원래 상태와 이유를 되돌려야 한다.** 토글은 더블클릭과 재시도가 잦아 실패가 눈에 띄지 않으면 사용자가 저장됐다고 믿는다.

### 불변식 — 코드가 지켜야 하는 것

32. `(freelancer_id, project_id)` 조합은 최대 1건이다.
33. 북마크의 `freelancer_id`는 역할이 `FREELANCER`인 사용자다.
34. 이 기능은 `projects`·`project_skills`에 **어떤 쓰기도 하지 않는다.**

## 다른 기능에 요구하는 것

| 무엇 | 담당 | 없으면 |
|---|---|---|
| 프로젝트 존재·삭제 여부 조회 | 유동우 (project-management) | 규칙 6·12·25를 판정할 수 없음 |
| 프로젝트 카드 표시 필드 | 유동우 | 북마크 목록·추천 목록을 그릴 수 없음 |
| `category` · `skills` · `createdAt` | 유동우 | 규칙 20·21의 우선순위 계산 불가 |
| 사용자 역할 확인 | 오민혁 (user-management) | 규칙 5의 프리랜서 판정 불가 |

**같은 담당자라도 포트를 거친다.** `prototype/server/ports/` 뒤에 두고 직접 import 하지 않는다 (ADR-0009). 나중에 두 도메인이 다른 서버로 갈라져도 이 파일만 바꾸면 된다.

## ORM만으로 보장되지 않는 것

| 불변식 | 규칙 | 상태 |
|---|---|---|
| `(freelancer_id, project_id)` 유일 | 32 | **ERD v1.4 에 `uq_bookmarks_pair` 로 이미 있다.** Prisma 의 `@@unique` 로 표현되므로 마이그레이션 SQL 을 손댈 필요 없다 |
| `freelancer_id`의 역할이 FREELANCER | 33 | ERD 의 I-13. `users.role` 을 참조하는 CHECK 를 걸 수 없어 **서비스에서 확인한다** |

**규칙 32의 UNIQUE 가 이 기능에서 특히 중요하다.** 토글 UI 는 더블클릭이 잦아 같은 요청이 거의 동시에 두 번 온다. 애플리케이션에서 "있는지 보고 없으면 넣는" 방식만으로는 두 요청이 둘 다 조회를 통과한 뒤 둘 다 삽입한다. 그러면 중복 행이 생기고, 그 뒤로는 "제거"를 눌러도 하나가 남는다.

**그래서 추가는 UNIQUE 위반을 잡아서 성공으로 처리한다.** 미리 조회해서 막는 것에 의존하지 않는다 — 조회와 삽입 사이의 틈을 없앨 수 없기 때문이다.

## 확정되지 않은 것

없다. PRD §4 의 규칙은 대부분 `CONFIRMED` 이고, `ASSUMPTION` 으로 표시된 것은 규칙 4(북마크는 실제 삭제) 하나다. 그 하나도 되돌리기 쉬운 결정이다.

다만 **PRD §4 자체가 이 프로젝트에서 근거가 가장 약한 장**이다. 위시켓 리서치가 북마크 동작을 `NOT VERIFIED` 로 남겼고, 추천은 위시켓의 "유사사례 검색 AI" 와 성격이 달라 `REFERENCE ONLY` 다. 여기 규칙은 대부분 RFP + 자체 설계다.

## 크기 기준

한 파일로 유지한다. 북마크와 추천이 별개 기능처럼 보이지만, 둘 다 "프리랜서가 프로젝트를 발견하고 담아두는" 하나의 흐름이고 읽는 데이터가 같다.

## 비고

- 북마크 마감 임박 알림(PRD B3-2)은 백로그다. 최윤석 담당이며 이 문서의 범위 밖이다.
- 추천을 상세 화면 하단에 두는 것은 RFP §3.2.1 의 화면 구성이다. 다른 위치에 재사용할 계획은 없다.
