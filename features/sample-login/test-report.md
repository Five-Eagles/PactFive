## spec.md 규칙별 확인

`spec.md`에는 규칙이 5개 있다. 규칙 5(Authorization 헤더)는 로그인 자체의 입출력이 아니라
"로그인 이후 다른 API를 어떻게 호출하는가"에 대한 설명이라, 이 Mock으로는 검증 대상이 아니다
(로그인 성공 시 토큰이 실제로 발급되는지는 규칙 4가 이미 확인한다). 나머지 4개는 전부 확인했다.

| spec 규칙 번호 | 어떻게 확인했나 | 결과 |
|---|---|---|
| 1 (계정 없음/비밀번호 불일치 → 401, 동일 메시지) | `run.tsx`의 "잘못된 비밀번호 거부됨" 테스트 | 통과 |
| 2 (탈퇴 계정 → 401, 동일 메시지) | `run.tsx`의 "탈퇴 계정 거부됨" 테스트 | 통과 |
| 3 (소셜 전용 계정 → 401, 동일 메시지) | `run.tsx`의 "소셜 전용 계정 거부됨" 테스트 | 통과 |
| 4 (성공 시 accessToken·refreshToken 발급) | `run.tsx`의 "정상 로그인" 테스트 | 통과 |
| 5 (Authorization: Bearer 헤더 사용) | 이 기능(로그인) 자체의 검증 대상 아님 — 로그인 이후 다른 API의 규칙 | 안 함 (해당 없음) |

## ux-philosophy.md §6 자체 점검 (`design/`이 있는 기능만 — 백엔드 전용 기능은 "해당 없음")

| 검증 항목 | 이 화면에서 어떻게 충족하는가 (또는 왜 못 하는가) |
|---|---|
| 상태 이해 | 제출 중(`isSubmitting=true`)에는 버튼이 비활성화돼 진행 상태를 보여준다. 다만 계정없음·비번불일치·탈퇴계정·소셜전용 4가지 실패 사유를 전부 "이메일 또는 비밀번호가 올바르지 않습니다"로 통일했다(spec 규칙 1~3) — 정확한 실패 사유까지는 알려주지 않는다. **의도된 트레이드오프**: `ux-philosophy.md` §5 우선순위 1번(개인정보 피해 방지 — 계정 존재 여부로 추측 가능한 정보 유출 방지)이 3번(상태·근거 이해)보다 앞선다. |
| 근거 이해 | 로그인은 추천치·산정값이 없는 단순 인증이라 이 항목은 적용 범위가 좁다. 성공 시 accessToken·refreshToken 발급 여부(spec 규칙 4)로 성공/실패가 명확히 갈린다. |
| 작업 보호 | 미검증 — 실패 후 이메일 입력값이 폼에 남아있는지(비밀번호 재입력만 요구하는지)는 `prototype/`에서 확인하지 않았다. high-fi 전환 시 확인 필요. |
| 복구 가능성 | 미검증 — 실패 메시지 옆에 "비밀번호 찾기" 등 대안 경로가 있는지는 low-fi 단계에서 다루지 않았다. |
| 선택권 | spec.md 범위(이메일 로그인)만 다룬다 — 소셜 로그인과의 선택권 비교는 user-management 전체 스펙(다른 기능) 몫이라 이 화면 단독으로는 해당 없음. |
| 비파괴성 | 로그인 시도 자체는 되돌릴 수 없는 결과를 만들지 않는다 — 해당 없음(위험 낮음). |
| 접근 가능성 | 미검증 — label과 input의 실제 연결(`for`/`id` 또는 `aria-label`), 키보드 탐색 순서는 low-fi 와이어프레임 단계에서는 확인 대상이 아니었다. high-fi/`prototype/web/` 구현 시 확인 필요. |

이 표 자체가 예시다 — "충족" 칸을 전부 채우는 게 목적이 아니라, 미검증인 항목은 미검증이라고
솔직히 남기는 게 핵심이다(위 spec.md 규칙별 확인과 같은 원칙).

## 아직 안 되는 것 (Known Issues)

- `prototype/server/`는 구현 초안 코드일 뿐 실제 DB에 연결돼 있지 않다 (의도된 상태 — ADR-0006).
  `auth.repository.ts`는 호출하면 "not implemented" 에러를 던진다.
- 비밀번호 해시 비교(`checkPassword`)가 실제 bcrypt 등이 아니라 문자열 비교 자리표시자다.
  통합 단계에서 팀장이 실제 구현으로 교체한다.
