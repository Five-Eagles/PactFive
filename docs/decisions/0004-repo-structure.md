# ADR-0004: PactFive 리포지토리 폴더 구조

| 항목 | 내용 |
|---|---|
| 상태 | 제안 (팀 확정 전) |
| 작성 | 팀장 + AI 협업자 (초안) |
| 날짜 | 2026-08-11 |
| 관련 결정 | ADR-0001 MVP 스코프, ADR-0002 역할 분담, ADR-0003 프로젝트 상태 DB 설계 |

---

## 1. 배경 (Context)

PactFive는 22일·198시간 동안 5명이 만드는 풀스택 마켓플레이스 MVP입니다. 이미 두 가지가 정해졌습니다.

- 역할 분담은 **기능(Feature) 단위**로 한다 (ADR-0002)
- 팀원 대부분은 **git 협업이 처음**이고, 비전공자가 다수다

이 두 조건이 겹치면 "5명이 각자 담당 기능을 개발하다가, 합치는 시점에 문제가 몰린다"는 리스크가 생깁니다. 이 문서는 그 리스크를 낮추기 위해 리포지토리를 왜 지금 구조로 설계했는지 정리한 기록입니다.

---

## 2. 문제 정의 (Problem)

| 문제 | 설명 |
|---|---|
| 정합성 병목 | 각자 AI 도구로 빠르게 코드를 생성하면 개인 속도는 빨라지지만, 서로 다른 가정으로 만든 결과물이 합쳐질 때 충돌·불일치가 몰릴 위험이 있음 |
| Git 협업 미숙 | 브랜치 충돌 해결 경험이 없는 팀원이 대부분이라, 큰 충돌이 한 번에 발생하면 진행이 멈출 수 있음 |
| 여러 AI 툴 사용 | 팀원마다 Claude Code, Cursor, Copilot 등 다른 AI 코딩 툴을 쓸 수 있어, 규칙을 어떻게 공통으로 지킬지 불명확함 |
| 문서-코드 불일치 | 시간이 지나면 문서가 실제 코드보다 낡아져서, 사람이든 AI든 잘못된 정보를 기준으로 작업하게 될 위험 |

**(Fact)** RFP는 스프린트 1·2 종료 시점(약 12일차)에 회원가입~알림까지 전체 플로우가 **실제로 통합되어 동작**해야 한다는 수용 기준을 명시하고 있습니다. 즉 "각자 만들고 마지막에 한 번에 합친다"는 방식은 이 요구사항과 정면으로 충돌합니다.

---

## 3. 검토한 대안 (Options)

### 대안 A — 팀장이 ERD·RFP 해석·디자인 시스템을 전부 작성, 팀원은 스펙/코드만 담당
장점: 속도, 일관성. 단점: RFP가 "엔티티 설계는 팀 ERD 설계 단계"라고 명시하고 있고, 데이터 모델링이 팀 전체의 학습 목표로 되어 있어 팀원이 이 과정을 건너뛰게 됨. **기각.**

### 대안 B — 컨벤션·역할 분담 없이 한 명이 AI로 풀스택 전체를 생성
장점: 사람 간 정합성 문제가 원천적으로 없음. 단점: 제출 산출물(스프린트 회고록 2회 이상, 팀원별 역할 분배)이 성립하지 않고, 198시간 안에 결제·계약·AI분석까지 포함된 코드를 혼자 리뷰·디버깅해야 하는 단일 실패점이 생김. **기각.**

### 대안 C — `features/` 폴더에 실제 프로토타입 코드를 넣고 나중에 `app/`에 통합
장점: 각자 독립적으로 테스트 가능. 단점: 통합 시점에 한 번도 합쳐본 적 없는 코드를 합치게 되어 오히려 더 큰 충돌 위험(빅뱅 통합)이 생기고, 스프린트별 통합 동작 요구사항과 충돌. **기각.**

### 대안 D (채택) — `features/`는 스펙·와이어프레임 전용, 실제 코드는 `app/` 안에서 기능별 폴더로 격리 + 프론트-백엔드는 계약(mock) 기반으로 분리 + 통합은 일 단위로 소규모 반복
장점: 개인 속도(AI 활용)와 팀 정합성을 동시에 확보. 단점: 초기 설계·문서화 비용이 들고, 매일 통합하는 루틴을 실제로 지켜야 효과가 있음. **채택.**

---

## 4. 비교 (Comparison)

### 4.1 코드 위치: features/에 프로토타입 코드 vs app/에서 격리 개발

| 기준 | features/에 프로토타입 코드 | app/에서 Feature 폴더로 격리 |
|---|---|---|
| 개인 테스트 가능 여부 | 가능 | 가능 (mock 또는 로컬 실행) |
| 통합 시점 리스크 | 높음 (한 번도 안 합쳐본 코드를 합침) | 낮음 (매일 조금씩 합쳐짐) |
| 스프린트 수용 기준 충족 | 어려움 | 자연스럽게 충족 |

### 4.2 통합 주기: 막판 1회 vs 페이즈 끝(5일) vs 일 단위

| 기준 | 막판 1회 | 페이즈 끝(5일 단위) | 일 단위 (채택) |
|---|---|---|---|
| 충돌 1회 크기 | 매우 큼 | 중간 | 작음 |
| Git 미숙 팀원 대응 난이도 | 매우 어려움 | 중간 | 쉬움 (충돌이 작아서 학습하며 해결 가능) |
| 문제 발견 시점 | 마지막 (수정 시간 없음) | 5일 지연 | 당일 (원인 파악 쉬움) |
| 필요한 프로세스 | 없음 | 낮음 | 매일 병합 루틴 필요 |

## 5. 최종 구조 (Decision)

```
pactfive/
├── README.md, AGENTS.md, .gitignore, .env.example
├── .github/CODEOWNERS, workflows/{ci.yml, deploy.yml}
├── sdd-framework/            # SDD 철학·규칙, 스펙/AGENTS 템플릿, 스펙 변경 신청 템플릿
├── design-system/            # 디자인 컨셉 명세
├── docs/
│   ├── domain/                # ERD·API 계약·상태 모델 (Feature 간 공유 자산) + change-requests/
│   ├── meetings/               # 회의록
│   └── decisions/              # ADR (이 문서 포함)
├── users/                     # 팀원별 담당 범위·권한 명세
├── features/                  # 기능별 스펙 + 와이어프레임 + 디자인 프로토타입 (코드 없음)
│   └── (8개: user-management / project-management / applications /
│           notifications / engagement / ai-pricing /
│           contracts-payments / reviews)
└── app/                       # 실제 구현 (클라이언트/서버, 각각 Feature 폴더로 격리)
    ├── web/  (mocks/ 포함 — 계약 기반 프론트 개발)
    └── server/  (prisma/ 포함 — 스키마는 별도 변경 절차 적용)
```

**8개 Feature 분할 근거**: RFP 3.1~3.7 기능 구분을 기준으로 하되, 3.2에 포함된 지원 관리(3.2.4)를 `applications`로 분리했습니다. 지원/수락/거절 흐름이 프로젝트 CRUD와 성격이 달라 별도 담당이 자연스럽기 때문입니다.

**인원 배분(의견, 팀 확정 필요)**: 5명 기준으로 contracts-payments·project-management는 단독 담당, applications+notifications는 상호작용이 강해 한 명이 함께, engagement+reviews는 상대적으로 가벼워 한 명이 함께, user-management는 다른 모든 기능이 의존하므로 최우선으로 먼저 끝내는 것을 권장합니다.

## 6. 리스크와 대응 (Risk & Mitigation)

| 리스크 | 대응 |
|---|---|
| 준비 단계 과부하 | 구조는 AI가 즉시 생성하되, 팀원은 온보딩 체크리스트(PR 1회 실습)로 사용법만 익힘 |
| user-management가 다른 기능을 막음 | 고정 테스트 토큰(`Bearer {testToken}`, 역할별 2~3개)으로 임시 인증 제공, 실제 인증과 `req.user` 계약만 고정 |
| 인원수 대비 8개 폴더 불균형 | 복잡도 기준 가중치 배분(위 5절 참고), 팀 논의로 최종 조정 |
| 프론트엔드/백엔드 리포 제출 요건 | 모노레포 유지 + README에 리포 링크 1개·배포 URL 2개(프론트/백엔드) 구분 명시 |
| mock과 실제 API 불일치 | 공유 타입(TypeScript/OpenAPI)로 컴파일 단계에서 강제 검증 + 일 단위 통합 시 AI가 diff와 상태 모델을 대조 검토 |
| .env 등 시크릿 노출 | `.gitignore`에 `.env` 계열 차단, `.env.example`만 예외 허용 |
| 문서(AGENTS.md 등) 노후화 | 공유 스펙 변경 시 `sdd-framework/templates/spec-change-request-template.md` 기반 신청서를 먼저 병합해야 실제 스펙 파일 수정이 승인되는 절차 도입 |

## 7. 다음 액션 (Next Action)

1. 팀원별 `users/이름.md` 작성 및 Feature 담당 확정 (가중치 배분 논의)
2. `docs/domain/` ERD·API 계약·상태 모델 초안 작성 → 팀 리뷰
3. `.github/CODEOWNERS`에 실제 담당자 반영, 브랜치 보호 규칙 설정
4. 각 폴더 `AGENTS.md` 내용 채우기 (툴 공통 지침, 폴더 지도)
5. 온보딩 PR 1회 실습으로 전체 워크플로우 손에 익히기

> **후속 결정**: `app/`, `docs/domain/` 접근 권한(팀장 전용 반영)은 ADR-0006에서 별도로 확정했습니다. (2026-08-19)
