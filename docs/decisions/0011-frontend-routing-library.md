# ADR-0011: 프론트엔드 라우팅 라이브러리 — React Router (잠정 확정)

| 항목 | 내용 |
|---|---|
| 상태 | 잠정 확정 |
| 작성 | 팀장 + AI 협업자 |
| 날짜 | 2026-08-27 |
| 관련 결정 | ADR-0006(app/ 접근 제한), ADR-0007(모노레포·서버리스), `app/web/AGENTS.md` |

---

## 1. 배경 (Context)

`app/web`에 8개 기능을 통합하려면 화면 간 이동(라우팅)을 처리할 방법이 필요하다. 지금까지
`features/*/prototype/web/`은 화면 컴포넌트 하나씩만 만들었고(프리뷰 하네스가 직접 렌더링),
라우팅을 다룬 적이 없다. 리포 어디에도 라우팅 라이브러리 의존성이 없다(2026-08-27 확인).

## 2. 문제 정의 (Problem)

라우팅 방식을 정하지 않으면 통합 시 기능마다 다른 방식으로 화면 이동을 구현하게 되고,
`App.tsx`에서 하나로 합칠 수 없다.

## 3. 검토한 대안 (Options)

| 대안 | 장점 | 단점 |
|---|---|---|
| **A. React Router (채택)** | React 생태계에서 가장 널리 쓰여 AI·검색 자료가 압도적으로 많다. Vite+React에 추가 설정이 거의 없다. | 최신 버전 간 API 변화가 있어 오래된 예제와 섞이면 혼란이 생길 수 있다. |
| B. TanStack Router | 타입 안전성이 강하다. | 자료가 상대적으로 적다 — 비전공자 팀이 AI 도움을 받을 때 불리하다. |
| C. 라이브러리 없이 직접 구현 | 의존성이 없다. | 뒤로가기·중첩 라우트·경로 파라미터를 직접 다뤄야 한다. 22일 일정에 맞지 않는다. |

## 4. 결정 (Decision)

**대안 A(React Router)를 잠정 확정한다.**

팀 전원이 React 비전공자라는 점이 결정적이었다 — 이 상황에서는 기술적 우열보다 **막혔을 때
찾을 수 있는 자료의 양**이 더 중요하다. 이 항목에서 A가 확실히 앞선다.

**교체 가능하도록 추상화하지 않는다.** 라우터 API는 화면 전반에 스며드는 성격이라 감싸는
비용이 교체 이득보다 크다 (`constitution.md` 원칙 6). 대신 값싼 격리만 한다 — 라우트 정의는
`App.tsx`와 각 기능의 `{도메인}.routes.tsx`에만 두고, 화면 컴포넌트에 경로 문자열을
하드코딩하지 않는다. 자세한 규칙은 `app/web/AGENTS.md`.

## 5. 남은 리스크 (Risk — 미해결)

- 이 결정은 **비교 검토를 깊게 거치지 않은 잠정 확정**이다. 팀 전원이 비전공자라 어느 쪽이든
  학습 비용이 비슷하고, 이 시점에 시간을 더 쓰는 것보다 확정하고 진행하는 편이 낫다는 판단이다.
- 추상화하지 않기로 했으므로, 교체가 필요해지면 화면 코드를 실제로 손봐야 한다. 이건 인지하고
  받아들인 트레이드오프다.

## 6. 재검토 조건 (이 조건에 해당하면 다시 논의한다)

"문제가 생기면 바꾼다"는 기준은 사람마다 달라 재논의가 반복되므로, 아래를 미리 정해둔다.

- 인증 상태에 따른 화면 보호(로그인 안 한 사용자 차단)를 React Router로 구현하기 어려운
  구조적 문제가 드러날 때
- 라이브러리 자체 버그·호환성 문제로 통합이 하루 이상 막힐 때

위에 해당하지 않는 불편(문법이 낯설다, 예제가 헷갈린다 등)은 재검토 사유가 아니다.

## 7. 영향받는 문서

- `app/web/AGENTS.md` — 진입점 구조·격리 규칙
- `app/web/package.json` — 의존성 추가 (통합 스캐폴드 착수 시)
