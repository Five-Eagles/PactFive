# ADR-0008: 인증 방식 — Supabase Auth 채택 (자체 JWT 대신)

| 항목 | 내용 |
|---|---|
| 상태 | 확정 |
| 작성 | 팀장 + AI 협업자 |
| 날짜 | 2026-08-24 |
| 관련 결정 | ADR-0007 백엔드 배포 아키텍처, ADR-0002 역할 분담 |

---

## 1. 배경 (Context)

기술 스택 확정 논의에서 DB(Supabase)까지는 정했으나 인증 방식(로그인·세션·OAuth)이 미정이었다.
RFP §3.1.1(이메일 로그인, Access/Refresh Token 발급)·§3.1.2(소셜 로그인 OAuth 2.0, Google·Kakao
중 1종 이상)는 둘 다 "기본 필수"이며, §8.1 스프린트 1·2 종료 기준(마일스톤 M2, 2026-08-28)에
"이메일 및 소셜 로그인 모두 정상 동작"이 명시돼 있다. 이 ADR을 쓰는 시점(2026-08-24) 기준
M2까지 4일 남았다.

## 2. 문제 정의 (Problem)

인증을 자체 JWT(비밀번호 해싱·Access/Refresh Token 발급/재발급·OAuth 리다이렉트 흐름을 직접
구현)로 만들지, Supabase Auth(내장 로그인·세션·OAuth 프로바이더)로 위임할지 결정한다. 두 방식
모두 §3.1.1의 Access/Refresh Token 요구사항과 §3.1.2의 OAuth 요구사항을 충족해야 한다 — OAuth
자체는 어느 쪽을 고르든 피할 수 없는 필수 항목이라는 점이 이번 판단의 핵심 전제다.

## 3. 검토한 대안 (Options)

### 대안 A — 자체 JWT (비밀번호 해싱 + 직접 서명·검증 + OAuth 직접 연동)

장점: 벤더 종속이 없다. 탈퇴 계정 거부·소셜 전용 계정 거부 같은 도메인 규칙을 특별한 우회
없이 일반 코드로 구현할 수 있어 가장 유동적이다.

단점: Access/Refresh Token 발급·자동 재발급·로그아웃 무효화, Google·Kakao 각각의 OAuth
리다이렉트·토큰 교환을 전부 직접 구현해야 한다. Kakao는 Node 생태계 라이브러리가 Google
대비 정리가 덜 되어 있어 구현 소요 시간을 예측하기 어렵다. `prototype/run.tsx`의 Mock으로
미리 검증되지 않는 영역(실제 OAuth 서버 왕복)이 넓어, 문제가 배포 직전에야 드러날 위험이 있다.

### 대안 B — Supabase Auth (채택)

장점: Access/Refresh Token 발급·자동 재발급을 클라이언트 SDK가 처리한다. Google·Kakao 모두
공식 지원 프로바이더라 대시보드 설정만으로 연동된다. 검증해야 할 표면적이 좁아, M2까지 남은
일정 안에 "정상 동작"을 확인하기 유리하다.

단점: 탈퇴 계정 거부·소셜 전용 계정 거부 같은 PactFive 고유 규칙은 Supabase가 대신 판단해주지
않으므로, 로그인 성공 이후 앱 레이어에서 별도로 체크하는 코드가 여전히 필요하다. 벤더 종속이
생긴다(추후 다른 인증 체계로 이전할 경우 비용 발생).

## 4. 결정 (Decision)

대안 B(Supabase Auth)를 채택한다.

**이 결정은 담당자의 역량 문제가 아니라 일정 리스크 문제다.** RFP 기준 OAuth(Google/Kakao)는
누가 담당하든, 어느 설계를 택하든 반드시 만들어야 하는 기본 필수 항목이었고, M2(2026-08-28)까지
4일이 남은 시점이었다. 대안 A(자체 JWT)는 Mock으로 사전 검증되지 않는 실제 OAuth 연동 부분이
넓어 마감 직전에 문제가 드러나면 되돌릴 시간이 없다는 게 핵심 리스크였고, 대안 B(Supabase Auth)는
검증해야 할 범위가 좁아 같은 일정 안에서 리스크가 더 낮다고 판단했다. 두 대안 모두 기술적
구현 난이도 자체는 담당자가 감당 가능한 수준으로 봤으며, 이번 결정은 "누가 얼마나 잘 만들
수 있는가"가 아니라 "어느 설계가 짧은 일정 안에서 더 적은 위험으로 같은 요구사항을
만족하는가"를 기준으로 내렸다.

## 5. 남은 리스크 (Risk — 미해결)

- Kakao OAuth는 Supabase에서도 Kakao 개발자 앱을 "사업자" 상태로 전환해야 이메일 동의 항목을
  요청할 수 있다는 알려진 제약이 있다 — 이는 Supabase가 아니라 Kakao 플랫폼 자체 정책이라
  어느 설계를 택했어도 동일하게 존재했을 제약이다. Kakao 개발자 앱 사업자 전환 여부를 미리
  확인해야 한다.
- 탈퇴 계정 거부·소셜 전용 계정 거부 등 PactFive 고유 인증 규칙은 Supabase Auth 사용 여부와
  무관하게 앱 레이어에서 별도 구현이 필요하다 — `features/sample-login/`이 자체 JWT 방식으로
  되어 있어 Supabase Auth 방식으로 다시 써야 한다.
- Supabase Auth로 전환 시 향후 다른 인증 방식으로 이전하는 비용(벤더 종속)은 이번 결정에서
  받아들인 트레이드오프다.
