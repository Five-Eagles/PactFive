# ADR-0006: app/ 폴더 접근 권한 — 팀장 단독 반영 원칙

| 항목 | 내용 |
|---|---|
| 상태 | 확정 |
| 작성 | 팀장 + AI 협업자 |
| 날짜 | 2026-08-18 |
| 관련 결정 | ADR-0004 리포지토리 폴더 구조 (대안 C 재검토) |

---

## 1. 배경 (Context)

CODEOWNERS·브랜치 보호를 설계하는 과정에서, `app/`(`app/web/`, `app/server/` — 실제 구현 코드) 전체를 팀장만 수정할 수 있도록 강하게 제한하자는 요구가 나왔다. 팀원은 이 폴더에 대한 수정 권한을 갖지 않는다.

## 2. 문제 정의 (Problem)

"팀장만 수정"을 어떤 강도로 구현할지 두 방식을 검토했다.

## 3. 검토한 대안 (Options)

### 대안 A — 게이트 방식
팀원이 자기 브랜치에서 `app/`에 직접 코드를 작성해 PR을 내되, 팀장(CODEOWNERS) 승인 없이는 병합 불가 (GitHub 브랜치 보호).
장점: 매일 소규모 git merge 유지, ADR-0004 채택안(대안 D)과 그대로 정합.
단점: "팀원이 app/에 코드를 쓴다"는 사실 자체는 남아 요구사항의 문자 그대로의 의도를 완전히 충족하지 않음.

### 대안 B — 완전 차단 방식 (채택)
팀원은 `features/X/prototype/`에 구현 초안을 작성하고, 팀장이 매일 검토·반영해 `app/`에 직접 커밋한다.
장점: `app/` git 이력에 팀장 커밋만 남아 요구사항을 문자 그대로 충족. 팀원의 실수가 공유 코드베이스에 바로 반영되는 경로가 없음.
단점: ADR-0004가 이미 기각한 "대안 C"(`features/`에 프로토타입 코드를 두었다가 나중에 `app/`로 통합)와 구조적으로 동일 — 빅뱅 통합 위험 재발 가능.

## 4. 위험 재평가 — 대안 C와 무엇이 다른가 (Comparison)

**(Fact)** ADR-0004가 대안 C를 기각한 근거는 "통합 시점에 한 번도 합쳐본 적 없는 코드를 한 번에 합친다"는 점이었다.

**(Opinion, 팀장)** 이번 결정은 그 통합을 막판 1회가 아니라 매일 반복하는 것을 원칙으로 하므로 위험의 크기 자체는 낮아진다 — 이 판단은 타당하다. 다만 ADR-0004가 줄이려 했던 위험은 사실 두 종류였고, 이번 결정이 줄이는 정도가 서로 다르다.

| 위험 종류 | 대안 A(게이트)가 줄이는 방식 | 대안 B(완전 차단)가 줄이는 정도 |
|---|---|---|
| 충돌 크기 (하루치만 쌓임) | 매일 git merge로 자동 축소 | 매일 반영을 원칙으로 하면 동일하게 축소 가능 |
| 팀장의 처리 노동량 | git merge는 도구가 diff를 계산 → 검토만 하면 됨 | 팀장이 4명분 초안을 매일 읽고 직접 `app/` 코드로 재작성·이식해야 함 — 도구가 아닌 사람이 매번 수작업 |

**(Assumption, 미검증)** "충돌 크기"는 두 방식 모두 하루 단위로 억제되지만, "팀장 1인이 처리해야 하는 노동량"은 완전 차단 쪽이 구조적으로 더 크다. 이는 빅뱅 통합 위험과는 별개의 새로운 리스크(처리 용량 병목)이며, 이번 결정으로 완전히 해소된 것은 아니다.

## 5. 결정 (Decision)

대안 B(완전 차단 방식)를 채택한다. `app/web/`, `app/server/` 전체를 팀장 단독 커밋 영역으로 하고, 팀원은 `features/X/prototype/`에 구현 초안을 작성한다. 근거는 매일 반영 원칙 유지로 빅뱅 통합 위험이 낮다는 팀장의 판단(§4)이다.

## 6. 남은 리스크 (Risk — 미해결)

- 팀장의 하루 처리 용량이 팀원 4인의 하루 산출량을 감당하는지 아직 검증되지 않음. 초반 1~2일 실측 후 조정 필요할 수 있음.
- `features/X/prototype/`이 기존 리포 구조 문서에는 "디자인 프로토타입"으로 정의되어 있어, 이번 결정("실제 구현 초안 코드 소스")과 어긋남 — 문서 갱신 필요.

## 7. 영향받는 문서/구조 — 구현 기록 (참고용, 결정 내용 아님)

> 아래는 이 결정이 실제로 어떻게 실행됐는지에 대한 기록이다. §3~§6의 결정 내용을 바꾸는
> 것이 아니다 (`sdd-framework/adr-process.md`의 ADR 불변성 규칙 참고, 2026-08-20 추가).

- **`sync-log.md`** (루트, 신규): 기능별 "마지막으로 app/에 반영된 prototype 커밋"을 날짜순으로 기록하는 단일 파일. 8개로 쪼개지 않고 하나로 통합 — 같은 목적(팀장의 통합 상태 파악)의 정보는 한 곳에 모은다는 기존 원칙(index.md Option 2 선정 근거)과 동일하게 적용.
- **`scripts/mark-synced.sh`** (신규): `{기능} [비고]`를 인자로 받아 해당 기능 prototype 브랜치의 현재 커밋 해시를 `sync-log.md`에 자동으로 한 줄 추가. CI/CD에는 넣지 않고 팀장이 통합 커밋과 같은 시점에 직접 실행하는 셸 스크립트로 한정 (기존 "통합구현은 AI·수동" 원칙 유지, CI 자동화는 이 프로젝트 규모에 비해 과함).
- **통합 시 diff 활용**: git 히스토리는 선형이므로 `git diff <sync-log 기록 커밋>..<prototype HEAD>`로 중간 커밋 수와 무관하게 누적 변경분을 한 번에 확인 가능. 이 diff는 patch로 그대로 적용하는 게 아니라 AI에게 "변경 범위" 컨텍스트로 제공해 app/ 컨벤션에 맞게 재구현하는 용도로 사용.
- **`app/AGENTS.md`** (신규): 위 통합 워크플로우 전체를 팀장 전용 지침으로 문서화. root `AGENTS.md`가 아니라 nested AGENTS.md에 배치 — 이 내용은 app/ 작업(=팀장만 하는 작업)에만 관련되어, root에 두면 팀원 4명의 무관한 AI 세션에도 매번 로드되어 토큰 비용만 늘어남 (index.md Option 2 선정 때와 동일한 기준).
- **root `AGENTS.md`**: `app/AGENTS.md` 참고 포인터 한 줄 + `features/*/prototype/` 재정의(디자인 프로토타입 → 구현 초안 코드) 명시.
- **CODEOWNERS**: `/app/ @팀장` 단일 규칙으로 단순화 (`features/`는 기존대로 기능별 오너 유지) — 실제 GitHub 사용자명 반영은 GitHub 세팅 담당자 몫으로 남겨둠.
- **prototype 브랜치 규칙**: force-push(rebase 등) 금지 — `sync-log.md`에 기록된 커밋 해시가 무효해지는 것을 방지 (`app/AGENTS.md`에 명시).
