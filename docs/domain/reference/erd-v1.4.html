0. 방향 1차 검토

0.1 검토 대상 — "DBML로 작성해서 PNG/PDF로 낸다"

용어부터

DBML(Database Markup Language)은 데이터베이스 구조를 그림이 아니라 글자로 적는 문법입니다. "프로젝트 테이블에는 제목, 예산, 마감일이 있다"를 아래처럼 텍스트로 적어두면, dbdiagram.io가 그걸 읽어서 그림을 자동으로 그려줍니다.

Table projects {
  id            varchar(30)  [pk]      // pk = 이 테이블의 대표 식별자
  title         varchar(100) [not null]
  budget_amount integer      [not null]
}

즉 글자가 원본이고 그림은 결과물입니다. 이 순서가 왜 중요한지가 이 검토의 핵심입니다. 그림이 원본이면 수정할 때마다 도형을 다시 옮겨야 하고, 누가 무엇을 바꿨는지 추적할 수 없습니다.

0.2 한계 1 — DBML이 표현하지 못하는 규칙이 있다

PRD §6.3은 비즈니스 불변식 29개를 정의합니다. "이것만은 절대 깨지면 안 된다"는 규칙입니다. 그런데 이 중 상당수는 ERD 그림에 표현할 방법이 없습니다.

불변식그림에 나타나는가어떻게 지키나
I-01 이메일 중복 불가✅ 표현됨UNIQUE 제약 — 그림에 표시됨
I-09 같은 프로젝트에 한 번만 지원✅ 표현됨UNIQUE(project_id, freelancer_id)
I-04 거래 중이면 모집은 반드시 CLOSED❌ 안 됨DB의 CHECK 제약 — DBML 문법에 없음
I-10 수락된 지원은 프로젝트당 최대 1건❌ 안 됨부분 유니크 인덱스 — DBML 문법에 없음
I-07 프로젝트는 기술 1개 이상 필요❌ 안 됨관계형 DB가 원리적으로 강제하지 못함 → 애플리케이션 검증

🔴 여기서 실제로 생길 수 있는 사고

ERD 그림만 보고 구현하면 CHECK 제약이 통째로 빠집니다. 그러면 "모집 중인데 이미 계약이 진행 중인 프로젝트"처럼 존재해서는 안 되는 데이터가 DB에 들어갑니다. 데이터가 한 번 그렇게 들어가면, 나중에 화면에서 이상하게 보이기 시작했을 때 원인을 찾기가 매우 어렵습니다.

⚠️ 이건 DBML만의 문제가 아닙니다. 우리가 쓸 Prisma도 스키마 파일에 CHECK 제약을 표현하지 못하고, 부분 유니크 인덱스는 아직 정식 출시되지 않은 버전에서만 지원됩니다. 즉 도구 체인 전체가 같은 한계를 공유하므로, 아래 보완책은 ERD 단계에서 끝나는 게 아니라 구현 단계까지 이어져야 합니다.

✅ 보완책: DBML 파일 하단에 "DBML로 표현할 수 없어 글로 남기는 제약" 블록을 두고, CHECK 제약과 부분 인덱스를 SQL 그대로 적어뒀습니다 (§5에 같은 내용). 제약을 스키마 원본과 같은 파일에 두는 것이 핵심입니다. 다른 문서로 흩어지면 반드시 잊힙니다.

0.3 한계 2 — ERD와 실제 코드가 어긋날 수 있다

제출 체크리스트에 "ERD와 API 명세서가 최신 코드와 일치하나요?"가 있습니다. 그런데 dbdiagram.io는 코드를 읽지 않습니다. 개발 중 컬럼을 추가하면 사람이 DBML도 같이 고쳐야 합니다.

선택지방식장점단점
A. 수동 동기화 (권장)스키마를 바꾼 PR에 DBML 수정을 같이 포함시킨다추가 도구 없음 · 지금 당장 가능 · PR 리뷰에서 걸러짐사람이 빠뜨릴 수 있음
B. 코드에서 자동 생성Prisma 스키마 → DBML 자동 변환 도구 사용어긋날 일이 없음도구 설정 비용. 변환 품질 검증 필요
C. 발표 직전 1회 대조제출 전에 한 번 맞춰본다비용 최소개발 중에는 계속 어긋난 상태 → 팀원이 잘못된 ERD를 보고 구현

C만 하면 개발 기간 내내 ERD가 틀린 상태로 남아, 그걸 보고 구현한 사람의 작업이 헛돌 수 있습니다. A는 규칙 하나만 추가하면 되고 PR 리뷰에서 잡힙니다. 다만 "스키마를 바꾸면 DBML도 같은 PR에서 고친다"를 팀 규칙으로 명시해야 실제로 지켜집니다. → §7.2 #1

1. 확장성 설계 원칙

"확장성 있게"라는 요청을 그대로 받으면 위험합니다. 확장성은 공짜가 아니고, 대부분 지금의 단순함을 대가로 지불하기 때문입니다. 그래서 이 ERD는 아래 기준으로 "어디까지 확장을 준비할지" 선을 그었습니다.

1.0 선 긋는 기준

준비한다준비하지 않는다
RFP가 도전 과제로 이미 언급한 방향 (다회차 협상, 환불, 다회차 납품)RFP에 없는 상상 기능 (팀 계정, 마일스톤, 분쟁 처리 — PRD §6.8이 명시적으로 배제)
운영하면 반드시 생기는 것 (코드값 추가, 통화, 감사 기록)지금 규모에서 필요 없는 성능 최적화
제약만 풀면 확장되는 구조 (준비 비용 0)지금 테이블을 늘려야 하는 확장

🔑 가장 중요한 원칙(v1.2까지): 엔티티 수를 임의로 늘리지 않았습니다.

"확장성"을 이유로 테이블을 추가하면 §6.10의 담당자별 검증 범위가 깨지고, 팀원이 자기 담당 밖의 테이블을 떠안게 됩니다. 확장은 테이블을 늘리는 방식이 아니라, 나중에 늘릴 수 있는 형태로 지금 만드는 방식으로 준비했습니다.

v1.3 갱신 다만 "엔티티 수 자체를 17종으로 고정한다"는 원래 규칙은 PRD §6.1(D-62)에서 이미 폐기됐음이 v1.3에서 확인됐습니다(§8.2 E-22). 이 원칙에서 지금도 유효한 부분은 "새 엔티티는 반드시 담당자를 명시하고 §6.10 검증 범위에 추가한다"이고, "숫자를 고정한다"는 더 이상 유효하지 않습니다 — 이번 v1.3에서 auth_sessions·negotiation_offer 2종이 이 원칙에 따라 정식으로 신설됐습니다(19종).

1.1 원칙 7가지

원칙 1. 제약으로 MVP 범위를 표현한다 확장 지점

PRD는 "다회차 협상 미구현", "납품 최대 1건(MVP)"처럼 지금은 1건만이라는 제약을 여럿 둡니다. 이걸 테이블 구조로 굳히지 않고 유니크 제약 한 줄로 표현했습니다.

-- 지금 (MVP): 한 지원서에 합의는 최대 1건 (I-15)
agreements.application_id  UNIQUE

-- 나중에 다회차 협상으로 가려면
--   UNIQUE 제거 + round 컬럼 추가 → UNIQUE(application_id, round)
--   테이블 구조·화면·API는 그대로. 마이그레이션 한 번으로 끝난다.

같은 방식이 contracts(I-16) · payments(I-17) · deliveries(I-18)에 적용돼 있습니다.

원칙 2. "당시의 사실"은 참조가 아니라 값으로 박제한다 RECOMMENDATION

🔴 이게 없으면 생기는 사고

계약서 화면이 "프로젝트 제목"을 projects에서 매번 읽어오도록 만들면, 의뢰인이 나중에 제목을 수정했을 때 이미 체결된 계약서의 내용까지 바뀝니다. 계약서는 "그때 이렇게 합의했다"를 증명하는 문서인데, 과거가 흔들리면 문서로서 의미가 없습니다.

그래서 contracts에 project_title_snapshot · terms_snapshot을, pricing_analyses에 input_description을 뒀습니다.

참조(FK)는 "연결"을, 스냅샷은 "당시의 사실"을 담습니다. 둘은 서로를 대체하지 않습니다.

원칙 3. 값이 늘어날 것은 테이블로, 안 늘어날 것은 enum으로

enum: 미리 정해둔 값 목록 중에서만 고를 수 있게 하는 타입입니다. "모집 중 / 마감" 같은 것.

🟡 권한 회수 권장 — §5.1 "DB 보장" 오분류 정정 (오민혁 검토의견 MUST, §9 E-16)

컬럼 부재(updated_at/deleted_at 없음)는 UPDATE/DELETE 자체를 막지 못합니다. 진짜 강제하려면 애플리케이션 실행 role과 마이그레이션 소유자 role을 분리하고, 실행 role에서 아래 권한을 회수해야 합니다.

REVOKE UPDATE, DELETE ON reviews FROM app_role;
REVOKE UPDATE, DELETE ON contract_signature_audits FROM app_role;
REVOKE DELETE ON agreements, contracts, payments, deliveries FROM app_role;
REVOKE DELETE ON negotiation_offer FROM app_role;   -- v1.4, 제안 이력에도 I-21 준용

guard trigger로 대체해도 됩니다. FK는 가능한 곳에서 ON DELETE CASCADE 대신 RESTRICT/NO ACTION을 씁니다(예: 사용자 삭제 시 거래 이력이 조용히 함께 사라지는 것을 방지). 이 REVOKE 문이 실제 마이그레이션에 적용되기 전까지, I-19·I-21·I-23은 §4 표에서 "DB+App(권장)"으로 표기하되 사실상 App 단독 보장과 같다고 간주하세요.
