# PactFive UX 철학

- 문서 상태: v1.0
- 기준일: 2026-08-24
- 제품 컨셉: Trust by Evidence
- 적용 범위: 공개 탐색, 프로젝트 등록, 지원, 금액 합의, 계약, 결제, 작업, 납품, 리뷰
- 관련 정본: `../design-system/design-tokens.md`, `../docs/domain/prd.md`, `../../DESIGN_SYSTEM_STRUCTURE_PRD.md`

## 1. 핵심 철학 한 문장

> **근거·현재 상태·다음 행동으로 불쾌한 불확실성을 없앤다.**

이 철학은 사용자가 불안·의심·당혹감·통제 상실을 느끼지 않게 한다는 약속이다. PactFive가 말하는 편안한 경험은 모든 긴장을 없애는 경험이 아니다. 결제, 계약, 취소처럼 주의가 필요한 순간은 분명하게 알리되, **이유를 알 수 없고 되돌아갈 길도 없는 불필요한 마찰**은 허용하지 않는 경험이다.

## 2. 왜 이 철학인가

### 확인된 사실 (FACT)

1. PactFive는 의뢰인과 프리랜서 사이의 프로젝트 탐색, 지원, 금액 합의, 계약, 결제, 납품을 중개한다.
2. 한 프로젝트 안에서도 모집, 거래, 지원, 합의, 계약, 결제, 납품 상태가 서로 독립적으로 변한다.
3. 사용자는 로그인, 역할 확인, 프로필 완성, AI 예산 분석처럼 본래 과업에서 잠시 벗어나는 흐름을 거칠 수 있다.
4. 예산, 지원 금액, 합의 금액, 결제 금액, 수수료, 예상 정산액은 의미와 확정 수준이 서로 다르다.
5. 지원 이후의 조건 변경, 오래된 합의 내용, 중복 제출, 취소와 서명의 동시 발생은 사용자의 동의와 결과에 직접 영향을 준다.

### 제품 판단 (OPINION)

1. 이 제품의 가장 큰 UX 위험은 기능 부족보다 **사용자가 현재 상황을 추측해야 하는 상태**다.
2. 신뢰는 친근한 문구나 장식만으로 만들어지지 않는다. 중요한 주장에 근거가 있고, 사용자가 그 근거를 이해하고 다음 행동을 선택할 수 있을 때 만들어진다.
3. 사용자가 느끼는 불쾌감은 대개 무시당함, 속았다는 느낌, 이유 없는 재입력, 갑작스러운 차단, 과도한 재촉, 되돌릴 수 없는 실수에서 시작한다.
4. 따라서 PactFive의 UX는 매 순간 **이해 가능성, 예측 가능성, 복구 가능성, 선택권**을 보장해야 한다.

## 3. 다섯 가지 원칙

### 원칙 1. 사용자에게 추측을 맡기지 않는다

**보장해야 하는 것**  
사용자는 지금 무엇이 진행 중인지, 어떤 일이 이미 일어났는지, 누구의 행동을 기다리는지, 언제까지 무엇을 할 수 있는지, 다음에 무엇을 해야 하는지 이해할 수 있어야 한다.

**왜 필요한가**  
중개 거래는 상대방과 시스템의 비동기 행동이 이어진다. 상태만 보이고 맥락이 보이지 않으면 사용자는 지연과 실패를 구분할 수 없다.

**평가 질문**

- 사용자가 도움말 없이 현재 상태를 자신의 말로 설명할 수 있는가?
- 다음 행동의 주체와 기한을 바로 찾을 수 있는가?
- 기다려야 하는 상황이라면 기다리는 이유와 이후 과정이 보이는가?

**현재 구현 예시 — 원칙 자체가 아닌 적용 사례**  
중간 결과물 검토 화면에서 현재 단계, 검토 기한, 상대가 남긴 기록, 검토 후 이어질 일을 한 흐름으로 보여준다.

### 원칙 2. 중요한 주장은 검증 가능한 근거에 연결한다

**보장해야 하는 것**  
금액, 경력, 검증, 승인, 변경, 완료와 같은 중요한 주장은 출처, 산정 이유, 기록 시각, 행위자 또는 실제 결과물 가운데 필요한 근거와 연결되어야 한다.

**왜 필요한가**  
근거 없는 확신은 거래가 커질수록 불신이 된다. 사용자는 결론뿐 아니라 그 결론을 믿거나 거절할 수 있는 이유가 필요하다.

**평가 질문**

- 이 숫자나 상태가 어디에서 왔는지 확인할 수 있는가?
- 시스템의 추천과 당사자가 확정한 사실이 구분되는가?
- 사용자가 근거를 보고 다른 선택을 할 수 있는가?

**현재 구현 예시 — 원칙 자체가 아닌 적용 사례**  
예산 분석에서 추천 금액만 제시하지 않고 산정 항목, 유사 프로젝트, 자료 기준 시점, 예상 범위와 직접 입력으로 돌아가는 선택을 함께 제공한다.

### 원칙 3. 이미 동의한 조건과 사용자의 작업을 보호한다

**보장해야 하는 것**  
사용자가 입력하거나 동의한 내용은 이동, 실패, 재시도 때문에 사라지지 않아야 한다. 중요한 조건이 바뀌면 이전 내용과 변경 사실을 추적할 수 있어야 하며, 오래된 정보에 대한 행동은 최신 사실을 확인한 뒤 이어져야 한다.

**왜 필요한가**  
프로젝트 조건과 금액은 계약의 전제가 된다. 과거의 동의를 조용히 덮어쓰거나 입력을 잃게 하면 사용자는 제품뿐 아니라 상대방도 신뢰하기 어렵다.

**평가 질문**

- 실패하거나 이전 단계로 돌아가도 작성 내용이 보존되는가?
- 변경 전후의 차이와 변경 주체를 확인할 수 있는가?
- 되돌릴 수 없는 행동 전에 영향받는 대상과 결과를 이해할 수 있는가?

**현재 구현 예시 — 원칙 자체가 아닌 적용 사례**  
지원이 시작된 뒤에는 합의의 전제가 된 일정과 예산을 임의로 바꾸지 못하게 하고, 변경이 필요하면 잠긴 이유와 가능한 후속 경로를 설명한다.

### 원칙 4. 막힘을 비난하지 않고 복구 가능한 경로로 바꾼다

**보장해야 하는 것**  
로그인 필요, 권한 부족, 미완성 정보, 빈 결과, 네트워크 실패, 오래된 정보처럼 흐름이 막히는 순간에도 사용자의 잘못처럼 말하지 않는다. 막힌 이유, 보존된 내용, 해결 방법, 돌아갈 위치를 함께 제공한다.

**왜 필요한가**  
오류 자체보다 무엇을 해야 할지 모르는 상태와 반복 입력이 더 큰 불쾌감을 만든다. 복구할 수 있다는 확신은 사용자가 과업을 계속하게 한다.

**평가 질문**

- 안내가 사용자를 탓하지 않고 해결 가능한 문장으로 쓰였는가?
- 사용자가 하던 일과 입력한 내용을 잃지 않고 복귀할 수 있는가?
- 같은 행동을 재시도해도 중복 결과나 추가 피해가 생기지 않는가?

**현재 구현 예시 — 원칙 자체가 아닌 적용 사례**  
프로젝트 지원 중 로그인이 필요해지면 로그인 완료 후 원래 프로젝트와 시작했던 행동으로 돌아오며, 이미 입력한 지원 내용은 유지한다.

### 원칙 5. 필요한 만큼만 드러내고 선택권을 보존한다

**보장해야 하는 것**  
사용자의 역할, 현재 과업, 결정의 중요도에 맞는 정보와 행동만 우선 제공한다. 필요하지 않은 내부 상태나 상대방의 비공개 정보는 노출하지 않으며, 추천이나 기본값은 사용자의 결정을 대신하지 않는다.

**왜 필요한가**  
정보가 많다고 투명한 것은 아니다. 관련 없는 정보와 과도한 행동은 판단을 어렵게 하고, 자동화가 선택권을 빼앗으면 편리함이 통제 상실로 바뀐다.

**평가 질문**

- 이 순간의 사용자에게 꼭 필요한 사실과 행동이 우선되어 있는가?
- 공개 정보와 거래 당사자만 알아야 하는 정보가 분리되는가?
- 추천을 거절하거나 직접 결정할 수 있는 경로가 있는가?

**현재 구현 예시 — 원칙 자체가 아닌 적용 사례**  
공개 프로젝트 탐색에서는 모집 판단에 필요한 정보만 제공하고, 계약·결제·거래 이력은 해당 당사자의 작업 영역에서만 보여준다.

## 4. 불쾌감을 만들지 않는 언어 원칙

1. 사용자를 탓하는 표현 대신 현재 상황과 해결 행동을 말한다.
2. 긴급성을 과장하거나 손실 공포로 행동을 재촉하지 않는다.
3. 기술 용어와 내부 오류 식별자는 기본 안내의 중심에 두지 않는다.
4. 위험과 제한을 숨기지 않되, 사용자가 이해할 수 있는 영향 단위로 설명한다.
5. 자동 추천은 확정된 사실처럼 말하지 않고 기준과 한계를 함께 밝힌다.
6. 성공을 과장하지 않고 실제로 완료된 범위만 말한다.

## 5. 의사결정 우선순위

두 설계안이 충돌할 때는 다음 순서로 판단한다.

1. 사용자의 금전·동의·개인정보 피해를 막는다.
2. 사용자가 하던 일과 이미 만든 내용을 보호한다.
3. 현재 상태와 판단 근거를 이해하게 한다.
4. 사용자가 복구하거나 다른 선택을 할 수 있게 한다.
5. 그다음에 속도, 편의, 시각적 즐거움을 높인다.

## 6. 검증 기준

| 검증 대상 | 성공 기준 |
|---|---|
| 상태 이해 | 사용자가 현재 상태와 다음 행동을 도움 없이 설명한다. |
| 근거 이해 | 금액·추천·승인의 출처와 확정 수준을 구분한다. |
| 작업 보호 | 실패, 이동, 재인증 이후에도 입력과 맥락이 유지된다. |
| 복구 가능성 | 오류·충돌·빈 상태 이후 제공된 경로로 과업을 이어간다. |
| 선택권 | 추천을 거절하거나 직접 입력·비교·취소할 수 있다. |
| 비파괴성 | 되돌릴 수 없는 결과를 실행 전에 이해하고 확인한다. |
| 접근 가능성 | 보조 기술, 키보드, 확대 환경에서도 같은 정보와 행동에 접근한다. |

## 7. 작성·검수 규칙

- 새 화면은 다섯 원칙 가운데 어떤 원칙을 어떻게 보장하는지 설명할 수 있어야 한다.
- 원칙과 충돌하는 편의 기능은 추가하지 않는다.
- 현재 구현 예시는 교체될 수 있으며, 원칙의 의미를 제한하지 않는다.
- 디자인 시스템의 특정 구성 요소, 색상값, 크기값이 바뀌어도 이 문서의 원칙은 유지되어야 한다.
- 확인된 사실, 가정, 제품 판단을 서로 구분한다.
