# feedback_loop/ — 통합 피드백 인덱스

## 왜 있는가

통합(`sdd-framework/integration-workflow.md`) 과정에서 팀장(+AI 협업자)은 각 담당자의
`prototype/`을 그대로 옮기지 않고 `app/`의 구조에 맞게 다시 구현한다. 이때 두 가지가 생긴다.

1. **공백 메우기** — 담당자의 `spec.md`/`api-contract.md`에 정의되지 않은 부분을 팀장이
   임의로 채워 넣는 경우.
2. **기능 간 충돌** — 두 기능의 API 계약·용어·상태 정의가 서로 어긋나 한쪽으로 맞춰야 하는 경우.

둘 다 **완벽한 설계보다 빠르게 통합·구현·피드백 루프를 도는 걸 우선한다**는 팀 원칙
(2026-08-26 회의)에 따라 통합을 멈추지 않고 진행한다. 대신 여기에 반드시 기록하고, 담당자가
다음 작업일에 검토해 자기 `spec.md`/`prototype/`을 고쳐나간다.

## 폴더 구조

```
feedback_loop/
  _template.md              # 새 피드백 작성 시 복사해서 쓰는 양식
  {YYYY-MM-DD}/
    {기능}.md               # 그 날짜 통합에서 {기능}에 대해 남긴 피드백
```

날짜 폴더는 통합이 실제로 일어난 날 기준으로 팀장이 만든다. 같은 날 같은 기능에 여러 건이
생기면 파일을 나누지 말고 한 파일에 항목(`## 항목 N`)으로 이어 붙인다.

---

## 피드백 상태 관리 (이 규칙이 이 문서의 핵심이다)

각 항목은 **상태 한 줄**을 갖는다. 담당자는 작업을 진행하면서 이 값을 직접 바꾼다.

```
상태: 미확인
```

| 상태 | 의미 | 누가 바꾸나 |
|---|---|---|
| `미확인` | 팀장이 방금 작성함. 담당자가 아직 안 읽음 | (팀장이 작성 시 기본값) |
| `검토중` | 담당자가 읽었고, 지금 반영 작업을 하고 있음 | 담당자 |
| `반영완료` | 담당자가 자기 `spec.md`/`prototype/`에 반영을 끝냄 | 담당자 |
| `재이슈` | 담당자가 이 결정에 동의하지 않아 대면 논의로 넘김 | 담당자 |

**형식을 지켜야 한다** — 줄 맨 앞이 `상태: ` 로 시작하고 위 4개 중 하나만 쓴다. 팀장이
미해결 항목을 한 번에 훑을 때 이 형식으로 검색하기 때문에, 자유 서술로 쓰면 누락된다.

```bash
# 팀장이 미해결 항목을 훑는 법 (날짜 폴더만 본다 — 이 README와 _template은 제외)
grep -rn "상태: 미확인\|상태: 검토중\|상태: 재이슈" feedback_loop/*/
```

### 파일 소유권 — 충돌을 막기 위한 분리

- **팀장**: 파일 생성, 항목 추가만 한다. 담당자가 바꾼 상태 값을 건드리지 않는다.
- **담당자**: `상태:` 줄과 자기 메모만 고친다. 항목 본문(Fact/근거)은 고치지 않는다.

담당자는 `develop`에 직접 push할 수 없으므로(pre-push 훅) 자기 feature 브랜치에서 상태를
바꾸고, 팀장이 다음 통합 때 `develop`으로 취합한다.

## 담당자 작업 흐름

`sdd-framework/feature-workflow.md`의 "시작하기 전에 확인할 것"에 이 단계가 들어 있다.
담당자의 AI는 **파일 원문을 그대로 보여주고 끝내지 않는다.** 순서는 이렇다:

1. `feedback_loop/`에서 자기 기능 이름의 파일을 **날짜 무관하게 전부** 찾는다.
   `상태: 반영완료`인 항목은 건너뛰고, 나머지(`미확인`/`검토중`/`재이슈`)만 대상으로 삼는다.
   — 하루를 건너뛰어도 놓치지 않는 건 이 규칙 덕분이다. "가장 최근 폴더만" 보지 않는다.
2. 대상 항목을 **먼저 검토한다** — 무엇이 왜 그렇게 채워졌는지 이해한다.
3. 사용자에게 **짧게 요약**해서 전달한다 (원문 전체를 붙여넣지 않는다).
4. **어떻게 반영할지 방향을 제안한다** — "이대로 spec.md 규칙으로 편입하는 게 맞아 보인다" /
   "원래 의도와 달라서 재이슈가 나아 보인다" 중 어느 쪽인지, 근거와 함께.
5. 사용자가 정하면 `상태:` 값을 바꾸고 작업을 진행한다. 작업을 시작하면 `검토중`, 끝내면
   `반영완료`, 동의하지 않으면 `재이슈`로 바꾼다.

`재이슈`로 바뀐 항목은 오전 회의에서 정한 대로 **연관 담당자 + 팀장이 대면**으로 해결한다.

## 팀장 작성 규칙

- 항목마다 **Fact**(원본에 없던 부분) / **어떻게 채웠는지**(파일 경로 포함) / **왜**(근거 —
  RFP·PRD 조항, 다른 기능과의 일관성, 또는 "근거 없음, 팀장 판단"이라고 솔직히) / **상태**를
  구분해 쓴다. 양식은 `_template.md`.
- 공백을 하나라도 채웠으면 남긴다 — "이슈가 없었다"와 "있었는데 기록 안 했다"는 다른 상태다
  (같은 원칙이 `test-report.md`에도 있다).
- 아무 공백도 없었으면 파일을 만들지 않는다(빈 파일을 쌓지 않는다).
- **기능 간 충돌은 한쪽에만 본문을 쓰고 다른 쪽엔 참조만 남긴다.** 양쪽에 같은 내용을 복사하면
  상태 값이 따로 놀아 어느 게 최신인지 알 수 없게 된다.

  ```
  ## 항목 2 — [충돌] applications ↔ project-management 상태 용어 불일치
  본문 위치: feedback_loop/2026-08-27/applications.md 항목 2 참조
  상태: 미확인
  ```

## 통합 중 막혔을 때 — 물어볼 것과 그냥 정할 것

통합하다 애매한 지점이 나올 때마다 멈춰서 물으면 통합이 진행되지 않는다. 오전에 정한 원칙
(빠른 확정 우선)과 일관되게 선을 긋는다.

| 되돌리기 비싼 것 → **멈추고 팀장에게 묻는다** | 되돌리기 싼 것 → **잠정 결정하고 feedback에 기록** |
|---|---|
| DB 스키마(테이블·컬럼) 변경 | 컴포넌트 분리 방식, 파일 배치 |
| API 엔드포인트 경로·요청/응답 형태 변경 | 내부 함수 구조, 변수명 |
| 도메인 용어 변경 (§3 표준 용어) | 에러 메시지 문구, 로딩·빈 상태 처리 |
| 기능 간 책임 경계 이동 | 스타일·레이아웃 세부 |
