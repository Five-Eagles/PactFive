1왜 이 문서인가 (Context)

오늘 점심 회의 안건은 두 가지다 — QA를 시작하기 전에 "입력값이 최소/최대 몇이어야 통과·거부되는지"를 팀 전체가 같은 기준으로 알고 있어야 하고, 담당자별로 어떤 계정으로 어떤 화면을 어떤 순서로 눌러봐야 하는지가 정리돼 있어야 한다. 여기에 더해, 어제 계정 부트스트랩을 고치면서 드러난 리스크 하나 (Supabase 이메일 발송 시간당 2통 제한)도 같이 등록해서 회의에서 결정한다.

Fact 아래 최소/최대 값은 전부 서버 코드의 상수·검증 로직에서 그대로 가져온 것이다(추정 아님) — application.constants.ts, project.service.ts, review.service.ts, auth.service.ts, pricing-analysis.constants.ts, notification.service.ts, public-api.service.ts, features/engagement/spec.md 직접 확인.

Fact 담당자 매핑은 docs/decisions/0002-role-division.md(ADR-0002, 2026-08-19 재구성) 기준으로 4명 체제다 — 오민혁(user-management·ai-pricing) · 유동우(project-management·engagement) · 최윤석(applications·notifications) · 조준영(contracts-payments·reviews). 전신 문서(9/9)는 최윤석 섹션이 없이 3명으로 돼 있었는데, 이번 문서에서 4명 체제로 바로잡았다.

2QA 최소·최대 요구조건 (안건 ①)

이 문서에서 말하는 최소·최대는 입력값의 최소·최대가 아니다. 최소 요구조건은 발표에서 보여 줄 수 있는 Happy case 데모 수준이고, 최대 요구조건은 실제 사용자가 입력·클릭·재시도하는 상황까지 포함하는 QA 수준이다. 아래 입력 경계값 표는 두 수준에서 공통으로 참고하는 별도 검증 자료다.

QA 수준 정의

최소 요구조건 — 발표용 Happy case: 준비된 계정으로 로그인하고, 대표 정상 흐름이 중단 없이 완료되어 화면·상태·핵심 결과를 시연할 수 있어야 한다.

최대 요구조건 — 실제 사용 수준: 무작위에 가까운 입력값과 사용자 액션(빈 값, 경계값, 긴 값, 반복 클릭, 새로고침, 뒤로가기, 권한 없는 접근, 네트워크 재시도)을 넣어도 오류가 설명되고 데이터·화면 상태가 안전하게 유지되어야 한다.

판정 원칙: 최소는 발표 차단 기준이다. 최대는 모든 입력을 통과시키라는 뜻이 아니라, 허용·거부 결과와 안내가 일관되고 재현 가능해야 한다는 뜻이다.

탭을 눌러 담당자를 전환한다. 각 탭은 담당 기능 → 실제 로그인 이메일이 있는 계정 → 순서대로 눌러볼 시나리오 → AI QA 프롬프트로 구성했다. 모든 담당자는 아래 공통 사전 검증을 먼저 실행한 뒤 담당 시나리오를 진행한다.

공통 AI QA 사전 검증 — Phase 0
당신은 PactFive QA 담당자입니다. 먼저 저장소 루트와 app/server를 확인하고 다음을 실행하세요.

1. 환경 파일: D:\projects\pact_five\.env가 존재하는지 확인하세요. 파일 내용과 시크릿 값은 출력하지 말고, WEB_ORIGIN, AUTH_PROVIDER_MODE, SUPABASE_URL, DATABASE_URL, DIRECT_URL, INTERNAL_SERVICE_TOKEN 등 필요한 키의 존재 여부만 PASS/FAIL로 기록하세요.
2. Prisma 준비: app/server에서 npm run prisma:generate를 실행하고 성공 여부를 기록하세요.
3. 실제 DB 연결: npx prisma migrate status를 실행하세요. 연결 실패·미적용 migration·schema 오류를 구분해 기록하세요.
4. 읽기 전용 DB 확인: Prisma schema의 users 테이블에서 count와 seed 계정 이메일 일부를 조회하세요. 비밀번호·토큰·DATABASE_URL은 절대 출력하지 마세요.
5. 로컬 계정: npm run seed:dev-accounts를 실행하세요. 이 명령은 idempotent이므로 기존 데이터를 삭제하지 않습니다. 성공 후 .dev-accounts.local.json에 계정 이메일이 생성됐는지만 확인하고, 실제 로그인은 각 계정의 이메일과 공통 비밀번호로 수행하세요.
6. API/UX 준비: 서버 health 응답, 로그인 성공, 새로고침 후 세션 유지 여부를 확인하세요. 이후 Phase 1 Happy case, Phase 2 경계·오류, Phase 3 실제 사용자 액션, Phase 4 UX 회귀 순서로 진행하세요.

각 단계에 PASS/FAIL, 실제 상태 코드, 화면 문구, 재현 단계와 스크린샷 위치를 기록하세요. 무작위 입력은 재현할 수 있도록 입력값과 액션 순서를 저장하세요.

5리스크 등록 — 이메일 인증 시간당 발송 제한

Problem

Fact 서버 코드(auth.service.ts)는 Confirm Email이 꺼져 있으면 회원가입 자체를 503 AUTH_CONFIGURATION_INVALID로 막도록 설계돼 있다 — 즉 이메일 인증은 지금 구조상 반드시 켜져 있어야 한다.

Fact Supabase 기본 이메일 발송(자체 SMTP)은 시간당 2통으로 제한돼 있다 (Supabase 공식 문서·GitHub 이슈로 확인). 실사용자가 동시에 여러 명 가입하면 3번째 요청부터 이메일이 발송되지 않는다.

Assumption 캡스톤 발표·시연 시점에 동시 가입자가 시간당 2명을 넘을 가능성 — 아직 정확한 동시 가입자 수 추정치는 없다. 팀 논의로 확인 필요.

Options

A. 이메일 인증을 회원가입 절차에서 제거

장점: 시간당 발송 제한 문제 자체가 사라진다. 가입 즉시 서비스 이용 가능(체감 속도 빠름). 추가 비용·설정 없음.

단점: 이메일 소유 확인 없이 계정이 만들어진다(오탈자·스팸 계정 위험). 비밀번호 재설정 등 이메일 기반 기능에 영향 가능성 — 별도 검토 필요. 현재 코드의 fail-closed 가드(503)를 되돌리는 설계 변경이 필요하다.

B. 이메일 발송 벤더 추가(커스텀 SMTP 연동)

장점: 시간당 30통까지 확보 가능 — 기존 인증 플로우·보안성을 그대로 유지한다. 코드 변경 범위가 작다(Supabase 대시보드 설정 위주).

단점: 벤더 가입·설정 작업 필요. 그래도 상한선은 남는다(시간당 30통) — 동시 가입자가 더 늘면 다시 논의 필요. 벤더에 따라 비용이 발생할 수 있다.

Comparison

기준A. 이메일 인증 제거B. SMTP 벤더 추가(30통/시간)
구현 난이도중 — fail-closed 가드 설계 변경하 — 설정 위주
보안·신뢰성낮음 — 이메일 미확인 계정 허용유지
확장성제한 자체가 없음시간당 30통 상한은 여전히 존재
비용없음벤더에 따라 발생 가능
개발 속도당장 빠름벤더 설정 시간 필요
팀원 이해 가능성쉬움쉬움
현재 프로젝트 규모 적합성캡스톤 규모엔 과함(보안 후퇴)일 수 있음규모에 맞는 절충안에 가까움

Opinion, 팀장 표만 보면 B가 더 균형 잡힌 절충안으로 보이지만, 이건 팀장 개인 의견이고 최종 결정은 아니다 — 아래처럼 결정을 보류하고 오늘 회의에서 팀이 정한다.

Decision — 보류 (오늘 회의에서 결정)

두 옵션(A: 이메일 인증 제거 / B: SMTP 벤더 추가) 중 하나를 오늘 회의에서 팀 합의로 정한다. 결정 후에는 이유·포기한 대안·가정을 Decision Log/ADR로 남긴다(운영 지침 §8).
