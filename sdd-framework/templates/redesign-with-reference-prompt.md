# 기존 구현 화면을 레퍼런스에 맞춰 재설계하는 프롬프트

> 용도: `design/*.html`·`prototype/web/*.tsx`를 이미 만들어 둔 기능 담당자가, 새로 고정된
> 공통 레퍼런스(`reference/project-management/*.html`)에 맞춰 **이미 만든 화면**을 다시
> 다듬을 때 씁니다. 처음부터 새 화면을 설계할 때 쓰는 프롬프트가 아닙니다 — 화면이 이미
> 있고, 그걸 프로젝트 전체와 같은 룩앤필로 맞추는 것이 목적입니다. (`reference/`에
> `project-management-bundle.html`도 있지만 그건 사람이 브라우저로 인터랙션을 확인할 때
> 쓰는 400KB짜리 단일 파일입니다 — 이 프롬프트는 그 파일을 읽게 하지 않습니다.)
>
> 사용법: 아래 코드 블록을 복사해서 담당 기능의 AI 툴(Claude, Cursor, Codex 등)에 그대로
> 붙여넣습니다. `{기능명}`만 자신의 기능(예: `contracts-payments`, `reviews`,
> `user-management`, `engagement`)으로 바꾸면 됩니다. 그 외 채워 넣을 값은 없습니다.

```
당신은 PactFive 프로젝트의 `{기능명}` 담당자 AI입니다. `features/{기능명}/design/`과
`features/{기능명}/prototype/web/`에 이미 화면을 만들어 두었습니다. 지금 할 일은 새 화면을
만드는 것이 아니라, **이미 만든 화면을 프로젝트 공통 레퍼런스에 맞춰 다시 다듬는 것**입니다.

## 0. 먼저 읽으세요 (실제로 파일을 열어서 확인하세요 — 이 프롬프트의 설명만으로 판단하지 마세요)

1. `reference/README.md` — 레퍼런스가 무엇이고, 왜 고정본인지, 어디까지가 확정 참고 대상인지
2. `reference/project-management/*.html` — **지금 만들거나 재설계하는 화면과 같은 유형의
   파일 하나(많아야 둘)만 골라서 여세요.** 7장을 전부 열지 않습니다. 아래 표로 고르세요 —
   `reference/README.md`에 같은 표가 더 자세히 있으니 애매하면 그쪽도 확인하세요.

   | 지금 만드는 화면 유형 | 볼 파일 |
   |---|---|
   | 대표·랜딩류 (히어로·배너·요약 카드) | `main.html` |
   | 목록·브라우즈류 (필터·정렬·카드 목록) | `browse.html` |
   | 상세류 (단일 항목 상세, 2단 레이아웃·사이드바) | `detail.html` |
   | 마이페이지·대시보드류 (탭 전환) | `mypage.html` |
   | 다단계 입력 폼 (등록·신청 등) | `register.html` |
   | 단일 항목 수정 폼 | `edit.html` |
   | 상태 전환·재개 액션 흐름 | `reopen.html` |

   **주의**: `detail.html`·`mypage.html`·`register.html`·`edit.html`·`reopen.html` 5장은
   `<style>` 블록의 CSS 규칙(간격·그리드 열 수 등)은 정적으로 들어 있지만, 그 클래스들이
   실제로 어떻게 조합돼 화면을 이루는지는 project-management의 JS 엔진(`demo/*.js`, 이
   폴더에는 없습니다)이 브라우저에서 렌더링해야 보입니다 — 이 5장에서는 CSS 규칙(값)만
   가져오고, 실제 조합·배치를 눈으로 봐야 한다면 `project-management-bundle.html`을
   브라우저로 직접 열어 확인하세요(사람이 하는 일입니다). `main.html`·`browse.html` 2장은
   정적 마크업 자체가 충분히 있어 파일만 읽어도 구조가 보입니다.

   **같은 폴더의 `project-management-bundle.html`(화면 10장을 base64 이미지까지 인라인한
   400KB 단일 파일)은 절대 통째로 읽지 마세요** — 사람이 브라우저로 인터랙션을 확인할 때 쓰는
   파일이지, AI가 구조를 읽는 용도가 아닙니다. 이 파일을 읽으면 컨텍스트 토큰을 크게
   낭비합니다. `experts`·`expert`·`guide` 3장(번들에는 있지만 개별 파일 폴더에는 없습니다)은
   ERD·PRD 근거가 없는 향후 검토 대상이니 참고하지 마세요.
3. `design-system/design-tokens.md` — 색·간격·컴포넌트 치수·모션 규칙의 **정본**입니다.
   레퍼런스와 이 문서가 다르게 보이는 부분이 있다면 이 문서가 이깁니다. 레퍼런스는 그 정본을
   "실제 화면에서 어떻게 조합해 쓰는가"를 보여주는 예시일 뿐, 색상·치수 값 자체의 정본이
   아닙니다.
4. `ux-philosophy/ux-philosophy.md` — 다섯 원칙과 §6 자체 점검 기준표.
5. `features/{기능명}/design/*.html` (지금 있는 전부) — **이 기능 자체의 화면 구조는 여전히
   이 파일들이 정본입니다.** 레퍼런스가 이걸 대체하지 않습니다. 레퍼런스는 "다른 기능과 같은
   제품처럼 보이는가"를 맞추는 참고 대상이지, 이 기능의 업무 규칙·데이터 구조를 바꾸라는
   지시가 아닙니다.
6. `features/{기능명}/prototype/web/*.tsx` (지금 있는 전부)
7. `features/{기능명}/spec.md`, `features/{기능명}/api-contract.md` — 재설계 과정에서
   업무 규칙이나 API 형태를 바꾸지 않습니다. 바뀌는 것은 화면의 **표현**뿐입니다.

## 1. 무엇을 맞추고, 무엇을 맞추지 않는가

**맞추는 것 — 여러 기능이 같은 제품처럼 보이게 하는 표현 요소:**
- 레이아웃 리듬 — 카드 간격·섹션 나누는 방식·페이지 폭(`--page-max`), 사이드바가 있다면
  sticky 처리 방식
- `design-tokens.md`에 있는 토큰을 실제로 어떻게 조합해 쓰는지(예: 보조 정보에 `.caption`을
  쓰는 패턴, 카드 그림자를 두 단계로만 쓰는 패턴)
- 되돌릴 수 없는 행동(삭제·취소·마감 등) 앞에 확인 요약을 두는 패턴 — 레퍼런스의
  `DestructiveActionSummary` 조합 방식(무엇이 되돌릴 수 없는지 → 영향받는 대상 → 확인
  버튼, 포커스는 "그만두기"에)
- 빈 상태·에러·로딩 상태를 보여주는 톤과 문구 스타일
- 모션 규칙(`design-tokens.md` §13) 적용 방식

**맞추지 않는 것 — 이 기능만의 것:**
- `{기능명}`의 업무 규칙(`spec.md`)·API 형태(`api-contract.md`) — 절대 바꾸지 않습니다
- `{기능명}` 고유의 데이터·용어·화면 구성 자체 — 레퍼런스가 project-management 화면이라고
  해서 그 도메인 용어나 화면 구성을 가져오지 않습니다
- 레퍼런스의 `experts`·`expert`·`guide` 3장 — 향후 검토 대상이라 참고 자료로 쓰지 않습니다

## 2. 절차

1. **차이 목록 작성 (Fact)** — 지금 `features/{기능명}/design/*.html`을 레퍼런스 7장과
   나란히 놓고, 위 "맞추는 것" 항목마다 지금 무엇이 다른지 구체적으로 적으세요. 느낌으로
   "비슷하다/다르다"가 아니라 무엇이 몇 px 다른지, 어떤 클래스를 안 쓰고 있는지 등 확인
   가능한 사실로 적으세요.
2. **바꿀 것 / 바꾸지 않을 것 (근거)** — 차이 목록 각각에 대해 레퍼런스에 맞출지, 아니면
   `{기능명}`의 특성상 다를 수밖에 없는지 판단하고 근거를 적으세요. 확신이 없는 항목은
   "확신 없음"이라고 표시하고 §4로 넘기세요 — 조용히 임의로 정하지 않습니다.
3. **`design/*.html`부터 고칩니다** — 이 기능의 화면 구조 정본이 `design/*.html`이므로,
   `prototype/web/`을 먼저 고치지 않습니다. 시안을 먼저 맞추고 코드를 시안에 맞춥니다.
4. **`prototype/web/*.tsx`를 갱신된 시안에 맞춰 다시 구현합니다.**
5. **`npx tsx prototype/run.tsx`를 다시 돌립니다.** `spec.md` 규칙 테스트가 전부 여전히
   통과해야 합니다 — 표현만 바꾸는 작업이므로 업무 규칙 테스트가 깨지면 표현을 바꾸다가
   규칙을 건드린 것입니다. 원인을 찾아 되돌리세요.
6. **`test-report.md`의 §6 자체 점검(ux-philosophy §6 기준표)을 다시 채웁니다.** 재설계로
   좋아지거나 나빠진 항목이 있으면 갱신하세요.

## 3. 확신 없는 지점 처리

레퍼런스의 패턴이 `{기능명}`에는 안 맞는다고 판단되면, 조용히 무시하지도 말고 임의로
따르지도 마세요. `features/{기능명}/change-requests/`에 `sdd-framework/templates/
spec-change-request-template.md` 형식으로 기록하세요 — 무엇이 안 맞는다고 판단했는지,
왜 그렇게 판단했는지, 팀장 확인이 필요한지를 적습니다.

## 4. 출력 형식

작업을 시작하기 전에 먼저 아래를 순서대로 답변으로 제시하세요 — 사용자가 승인하면 그다음에
실제로 파일을 고칩니다.

1. **차이 목록 표** — 열: 항목 / 지금 상태 / 레퍼런스 상태 / 맞출지 여부(예·아니오·확신 없음)
2. **확신 없음으로 분류한 항목** — 왜 확신이 없는지, change-requests로 올릴지 여부
3. **고칠 파일 목록** — `design/*.html` 중 무엇을, `prototype/web/*.tsx` 중 무엇을
4. 사용자 승인 후 실제 수정 → `run.tsx` 재실행 결과(PASS/FAIL 개수) → `test-report.md` §6
   갱신까지 마치고 마지막에 요약 보고
```

### 설계 메모

- 이 프롬프트는 **표현(레이아웃·토큰 사용·확인 패턴·톤)만** 맞추도록 범위를 좁혔습니다.
  업무 규칙·API 형태까지 건드리게 하면 `feature-workflow.md`가 정한 "SPEC은 담당자 소유"
  원칙과 충돌하고, 재설계 작업이 도메인 로직 변경으로 번질 위험이 있습니다.
- "먼저 차이 목록과 계획을 제시하고 승인받은 뒤 고친다"로 절차를 나눈 것은, 이 프로젝트가
  일관되게 따르는 "근거 → 비교 → 결정" 순서를 재설계 작업에도 그대로 적용한 것입니다 — AI가
  일방적으로 다 고쳐버리면 담당자가 무엇이 왜 바뀌었는지 확인할 기회가 없습니다.
- `reference/`의 3장(experts·expert·guide)을 참고하지 말라는 지시를 반복해서 넣었습니다 —
  번들 파일을 열면 10장이 다 보이므로, 범위 제한을 §0과 §1 두 곳에 명시하지 않으면 AI가
  10장을 전부 확정 패턴으로 오인하기 쉽습니다.
- change-requests 경로를 안내한 것은, 이미 프로젝트에 있는 CR 메커니즘(지금까지 유동우가
  써 온 방식)을 그대로 재사용하기 위함입니다 — 재설계 과정에서 나온 새로운 판단 필요 지점을
  담기 위해 별도 문서 체계를 새로 만들지 않았습니다.
