# 기존 구현 화면을 레퍼런스에 맞춰 재설계하는 프롬프트

> 용도: `design/*.html`·`prototype/web/*.tsx`를 이미 만들어 둔 기능 담당자가, 새로 고정된
> 공통 레퍼런스(`reference/project-management/*.html`)에 맞춰 **이미 만든 화면**을 다시
> 다듬을 때 씁니다. 처음부터 새 화면을 설계할 때 쓰는 프롬프트가 아닙니다 — 화면이 이미
> 있고, 그걸 프로젝트 전체와 같은 룩앤필로 맞추는 것이 목적입니다. (`reference/`에
> `project-management-bundle.html`도 있지만 그건 사람이 브라우저로 인터랙션을 확인할 때
> 쓰는 400KB짜리 단일 파일입니다 — 이 프롬프트는 그 파일을 읽게 하지 않습니다.)
>
> 사용법: 아래 코드 블록을 그대로 복사해서 담당 기능의 AI 툴(Claude, Cursor, Codex 등)에
> 붙여넣습니다. **미리 채워 넣을 값이 없습니다.** 예전 버전은 `{기능명}`을 사람이 직접 바꿔
> 넣어야 했는데, 그러지 않도록 바꿨습니다 — 이제는 AI가 먼저 리포를 스캔해 "지금 재설계가
> 필요해 보이는 기능" 후보를 목록으로 제시하고, 사용자는 그 목록에서 자신이 누구인지와 어떤
> 기능을 재설계할지 답하기만 하면 됩니다.

```
당신은 PactFive 프로젝트의 AI 툴입니다. 지금 할 일은 새 화면을 만드는 것이 아니라, **이미
만든 화면을 프로젝트 공통 레퍼런스에 맞춰 다시 다듬는 것**입니다. 누구의 어떤 기능을
재설계할지부터 아래 절차로 먼저 확인하세요 — 짐작으로 바로 진행하지 않습니다.

## 0. 먼저 스스로 확인하고, 사용자에게 확인받으세요

### 0-1. 이 세션이 누구인지 단서를 모으세요

- `git config user.name`, `git config user.email`을 실행하세요.
- 지금까지의 대화에 이미 담당자 이름이나 담당 기능이 언급됐다면 그것도 단서로 씁니다.
- 확실하지 않아도 됩니다 — 아래 0-3에서 사용자에게 직접 확인받습니다.

### 0-2. 재설계 후보 기능 목록을 만드세요

`features/` 아래에서, **이미 화면 설계와 구현 초안까지 있는 기능**을 후보로 봅니다 —
`design/`에 `.html`이 있고 `prototype/web/`에도 파일이 있는 폴더입니다. 아래 조건으로
직접 스캔하세요(하드코딩된 목록을 쓰지 않습니다 — 팀 배정은 스프린트 중에도 바뀝니다):

```bash
for f in features/*/; do
  name=$(basename "$f")
  [ "$name" = "project-management" ] && continue   # 레퍼런스의 출처 자체 — 재설계 대상 아님
  case "$name" in sample-login|login_sample_*) continue;; esac  # 연습용 예시 폴더
  design_n=$(find "$f/design" -maxdepth 1 -name "*.html" 2>/dev/null | wc -l)
  web_n=$(find "$f/prototype/web" -maxdepth 1 \( -name "*.tsx" -o -name "*.ts" \) 2>/dev/null | wc -l)
  if [ "$design_n" -gt 0 ] && [ "$web_n" -gt 0 ]; then
    echo "$name (design html=$design_n, prototype/web files=$web_n)"
  fi
done
```

`project-management`가 제외되는 이유: 레퍼런스 자체가 이 기능의 화면에서 나왔으므로
재설계 대상이 아닙니다. `design/`은 있는데 `prototype/web/`이 없는(또는 그 반대인) 기능은
"아직 구현 중"이라 이 프롬프트의 대상이 아닙니다 — 후보에서 뺍니다.

### 0-3. 후보마다 최근 작성자를 확인하세요

```bash
git log --format='%an <%ae>' -- features/{후보 기능명}/ | sort -u
```

0-1에서 확인한 세션 사용자와 겹치는 후보가 있으면 "이 세션과 일치"로 표시하고, 없으면
"다른 담당자로 보임"으로 표시하세요. **이건 힌트일 뿐 확정이 아닙니다** — 팀장이 통합
과정에서 커밋했을 수도 있고, 여러 사람이 한 폴더를 같이 건드렸을 수도 있습니다.

### 0-4. 사용자에게 제시하고, 직접 답을 받으세요

아래 형태로 표를 만들어 보여주세요.

| 후보 기능 | 재설계 후보인 이유 | 최근 작성자(git) | 이 세션과 일치 |
|---|---|---|---|
| (0-2에서 찾은 기능) | design+prototype 있음 | (0-3 결과) | 예/아니오 |

표를 보여준 다음, **반드시 아래 두 가지를 사용자에게 직접 물어보세요** — 추측한 값으로
바로 진행하지 않습니다.

1. "당신은 누구입니까? (이름 또는 담당 기능을 알려주세요)"
2. "이번에 재설계할 기능은 위 목록 중 무엇입니까? (여러 개를 골라도 됩니다)"

사용자가 목록에 없는 기능을 답하면 — 아직 `design/`·`prototype/web/`이 없어 후보에
안 잡혔을 수 있습니다. 그 경우 실제로 그 폴더에 두 가지가 다 있는지 다시 확인하고,
없다면 "이 기능은 아직 화면 구현이 없어 이 프롬프트의 대상이 아닙니다 — 새로 설계할 때
쓰는 프롬프트가 따로 필요합니다"라고 안내하고 멈추세요.

**기능을 여러 개 골랐다면, 기능마다 아래 1~5를 처음부터 따로 실행하세요** — 한 번에
섞지 않습니다. 화면 구조의 정본(`design/*.html`)이 기능마다 다르기 때문입니다.

## 1. 먼저 읽으세요 (실제로 파일을 열어서 확인하세요 — 이 프롬프트의 설명만으로 판단하지 마세요)

1. `reference/README.md` — 레퍼런스가 무엇이고, 왜 고정본인지, 어디까지가 확정 참고 대상인지
2. `reference/project-management/*.html` — **지금 만들거나 재설계하는 화면과 같은 유형의
   파일 하나(많아야 둘)만 골라서 여세요.** 7장을 전부 열지 않습니다. 아래 표로 고르세요 —
   `reference/README.md`에 같은 표가 더 자세히 있으니 애매하면 그쪽도 확인하세요.

   | 지금 만드는 화면 유형 | 볼 파일 |

7. `features/{기능명}/spec.md`, `features/{기능명}/api-contract.md` — 재설계 과정에서

## 2. 무엇을 맞추고, 무엇을 맞추지 않는가

**맞추는 것 — 여러 기능이 같은 제품처럼 보이게 하는 표현 요소:**
- 레이아웃 리듬 — 카드 간격·섹션 나누는 방식·페이지 폭(`--page-max`), 사이드바가 있다면
  sticky 처리 방식
- `design-tokens.md`에 있는 토큰을 실제로 어떻게 조합해 쓰는지(예: 보조 정보에 `.caption`을
  쓰는 패턴, 카드 그림자를 두 단계로만 쓰는 패턴)
- 되돌릴 수 없는 행동(삭제·취소·마감 등) 앞에 확인 요약을 두는 패턴 — 레퍼런스의
  `DestructiveActionSummary` 조합 방식(무엇이 되돌릴 수 없는지 → 영향받는 대상 → 확인
  버튼, 포커스는 "그만두기"에)
- 빈 상태·에러·로딩 상태를 보여주는 톤과 문구 스타일
- 모션 규칙(`design-tokens.md` §13) 적용 방식

**맞추지 않는 것 — 이 기능만의 것:**
- `{기능명}`의 업무 규칙(`spec.md`)·API 형태(`api-contract.md`) — 절대 바꾸지 않습니다
- `{기능명}` 고유의 데이터·용어·화면 구성 자체 — 레퍼런스가 project-management 화면이라고
  해서 그 도메인 용어나 화면 구성을 가져오지 않습니다
- 레퍼런스의 `experts`·`expert`·`guide` 3장 — 향후 검토 대상이라 참고 자료로 쓰지 않습니다

## 3. 절차

1. **차이 목록 작성 (Fact)** — 지금 `features/{기능명}/design/*.html`을 레퍼런스와 나란히
   놓고, 위 "맞추는 것" 항목마다 지금 무엇이 다른지 구체적으로 적으세요. 느낌으로 "비슷하다/
   다르다"가 아니라 무엇이 몇 px 다른지, 어떤 클래스를 안 쓰고 있는지 등 확인 가능한 사실로
   적으세요.
2. **바꿀 것 / 바꾸지 않을 것 (근거)** — 차이 목록 각각에 대해 레퍼런스에 맞출지, 아니면
   `{기능명}`의 특성상 다를 수밖에 없는지 판단하고 근거를 적으세요. 확신이 없는 항목은
   "확신 없음"이라고 표시하고 §5로 넘기세요 — 조용히 임의로 정하지 않습니다.
3. **`design/*.html`부터 고칩니다** — 이 기능의 화면 구조 정본이 `design/*.html`이므로,
   `prototype/web/`을 먼저 고치지 않습니다. 시안을 먼저 맞추고 코드를 시안에 맞춥니다.
4. **`prototype/web/*.tsx`를 갱신된 시안에 맞춰 다시 구현합니다.**
5. **`npx tsx prototype/run.tsx`를 다시 돌립니다.** `spec.md` 규칙 테스트가 전부 여전히
   통과해야 합니다 — 표현만 바꾸는 작업이므로 업무 규칙 테스트가 깨지면 표현을 바꾸다가
   규칙을 건드린 것입니다. 원인을 찾아 되돌리세요.
6. **`test-report.md`의 §6 자체 점검(ux-philosophy §6 기준표)을 다시 채웁니다.** 재설계로
   좋아지거나 나빠진 항목이 있으면 갱신하세요.

## 4. 확신 없는 지점 처리

레퍼런스의 패턴이 `{기능명}`에는 안 맞는다고 판단되면, 조용히 무시하지도 말고 임의로
따르지도 마세요. `features/{기능명}/change-requests/`에 `sdd-framework/templates/
spec-change-request-template.md` 형식으로 기록하세요 — 무엇이 안 맞는다고 판단했는지,
왜 그렇게 판단했는지, 팀장 확인이 필요한지를 적습니다.

## 5. 출력 형식

작업을 시작하기 전에 먼저 아래를 순서대로 답변으로 제시하세요 — 사용자가 승인하면 그다음에
실제로 파일을 고칩니다.

1. **후보 목록과 사용자 확인 결과** (§0) — 누구로 확인했는지, 어떤 기능(들)을 진행하는지
2. **차이 목록 표** (기능마다 따로) — 열: 항목 / 지금 상태 / 레퍼런스 상태 / 맞출지
   여부(예·아니오·확신 없음)
3. **확신 없음으로 분류한 항목** — 왜 확신이 없는지, change-requests로 올릴지 여부
4. **고칠 파일 목록** — `design/*.html` 중 무엇을, `prototype/web/*.tsx` 중 무엇을
5. 사용자 승인 후 실제 수정 → `run.tsx` 재실행 결과(PASS/FAIL 개수) → `test-report.md` §6
   갱신까지 마치고 마지막에 요약 보고 (기능을 여러 개 진행했다면 기능별로 각각 보고)
```

### 설계 메모

- **왜 담당자 이름을 하드코딩하지 않았는가.** 팀 배정은 이 스프린트 중에도 이미 한 번
  바뀌었다(9/3 재배정). 프롬프트 파일에 "user-management는 오민혁"처럼 박아 두면 다음
  배정 변경 때마다 이 파일도 같이 고쳐야 하고, 안 고치면 조용히 낡은 값을 알려주게 된다 —
  이 프로젝트가 CR-0011·PRD 담당 표에서 이미 겪은 문제와 같은 종류다. 대신 매번 실행 시점에
  `features/*/design/`·`prototype/web/`을 스캔해 후보를 계산하게 했다.
- **왜 git 작성자를 "확정"이 아니라 "힌트"로만 쓰는가.** 이 리포는 팀장이 통합 과정에서
  여러 기능 폴더에 커밋하기도 하고, AI 툴이 사람을 대신해 커밋하는 구조라 작성자 메타데이터가
  실제 담당자와 항상 일치하지 않는다. 그래서 세션 사용자와 겹치면 표시는 하되, 최종 확인은
  반드시 사용자에게 직접 묻게 했다.
- **왜 "목록에 없는 기능을 답하면 멈춘다"를 넣었는가.** `design/`·`prototype/web/`이 아직
  없는 기능(예: 재배정 직후라 아직 구현 전인 기능)에 이 프롬프트를 잘못 쓰면, AI가 없는
  화면을 "차이가 없다"고 잘못 판단하거나 새로 화면을 지어내기 쉽다. 이 프롬프트는 재설계
  전용이라 그 경우엔 명시적으로 멈추고 안내만 하게 했다.
- 이 프롬프트는 여전히 **표현(레이아웃·토큰 사용·확인 패턴·톤)만** 맞추도록 범위를
  좁혔습니다. 업무 규칙·API 형태까지 건드리게 하면 `feature-workflow.md`가 정한 "SPEC은
  담당자 소유" 원칙과 충돌하고, 재설계 작업이 도메인 로직 변경으로 번질 위험이 있습니다.
- "먼저 차이 목록과 계획을 제시하고 승인받은 뒤 고친다"로 절차를 나눈 것은, 이 프로젝트가
  일관되게 따르는 "근거 → 비교 → 결정" 순서를 재설계 작업에도 그대로 적용한 것입니다.
- `reference/`의 3장(experts·expert·guide)을 참고하지 말라는 지시를 반복해서 넣었습니다 —
  개별 파일 폴더에는 없지만 `bundle.html`을 열면 10장이 다 보이므로, 범위 제한을 여러 곳에
  명시하지 않으면 AI가 10장을 전부 확정 패턴으로 오인하기 쉽습니다.
- change-requests 경로를 안내한 것은, 이미 프로젝트에 있는 CR 메커니즘을 그대로 재사용하기
  위함입니다 — 재설계 과정에서 나온 새로운 판단 필요 지점을 담기 위해 별도 문서 체계를 새로
  만들지 않았습니다.
