## 1. 검증 대상 규칙 — `AGENTS.md` 원문 인용

아래는 루트 `AGENTS.md`에 실제로 적혀 있는 폴더·파일 구조 규칙입니다. 요약하지 않고 원문 그대로
가져왔습니다. 각 규칙에 ID를 붙였으니, 아래 §3에서 이 ID 순서대로 판정하세요.

**R1** — "각 기능이 어디에 있는지는 루트 `index.md` 참고"

**R2** — "`app/` 작업 규칙(접근 권한, 통합 워크플로우)은 `app/AGENTS.md` 참고"

**R3** — "도메인 공유 문서(ERD·API 계약) 통합 규칙은 `docs/domain/AGENTS.md` 참고"

**R4** — "공통 통합 워크플로우(diff 확인 → 반영 → sync-log 기록) 원리는 `sdd-framework/integration-workflow.md` 참고"

**R5** — "기능 담당자가 `features/{기능}/` 안에서 작업하는 순서(SPEC → API 계약/디자인 시안 →
Mock+구현 초안 코드)는 `sdd-framework/feature-workflow.md` 참고"

**R6** — "ADR을 새로 써야 할지 판단하는 기준은 `sdd-framework/adr-process.md` 참고"

**R7** — "새 문서를 만들지 기존 문서를 확장할지 판단하는 기준은 `sdd-framework/evolution-rules.md` 참고"

**R8** — "이름 규칙(변수·API·DB·Git)은 `docs/naming-convention.md` 참고"

**R9** — "PRD·ERD 요약은 각각 `docs/domain/prd.md`, `docs/domain/erd.md` 참고 (원본은 `docs/domain/reference/`)"

**R10** — "기능 담당자 워크플로우를 실제로 밟은 동작 예시는 `features/sample-login/` 참고 — 팀장과의
대화 없이 다른 AI가 작업해도 이 예시와 `sdd-framework/feature-workflow.md`의 완료 조건만으로
충분해야 한다"

**R11** — "`prototype/web/`을 브라우저에서 실제로 보고 싶으면 리포 루트에서 `npm run preview:dev`
(`tools/preview/`, 전체 기능 공용 프리뷰 하네스) 참고"

**R12** — "`features/{기능}/prototype/`은 디자인 프로토타입이 아니라 **실제 구현 초안 코드 + Mock
레포지토리**입니다 (ADR-0006, 2026-08-18 재정의). 화면 디자인 시안은 `features/{기능}/design/`에
작성하며, design-system 확정 전에는 low-fi, 확정 후에는 high-fi로 만듭니다. 팀원이 `prototype/`,
`design/`, `api-contract.md`, `spec.md`에서 작업하고, 팀장이 검토해 `app/`에 반영합니다. `app/`은
팀장만 직접 수정합니다."

**R13** — "design-system/, ux-philosophy/ ... 두 폴더는 의도적으로 분리되어 있습니다 — ux-philosophy는
design-system의 특정 컴포넌트와 결합되지 않도록 추상 수준을 유지합니다."

**R14** — "각 기능의 API 계약 문서는 `features/{기능}/api-contract.md`에 작성합니다. `docs/domain/api-spec/`는
팀장이 반영한 사본이며 팀원이 직접 수정하지 않습니다."

## 2. 설계 결정 근거 요약 (경계 케이스 판단용)

규칙과 실제 상태가 정확히 일치하지 않는 경계 케이스를 만나면, 아래 근거로 "의도된 예외"인지
"실제 위반"인지 판단하세요.

**ADR-0004 (리포 구조, 2026-08-11, 상태: 제안 — 아직 팀 확정 상태는 아니지만 실질적으로 전체
구조가 이 결정을 전제로 운영되고 있습니다):**
- 왜 이런 구조가 필요했는가: 5명이 22일 동안 기능 단위로 나눠 만드는데, 팀원 대부분이 git 협업이
  처음이고 비전공자가 다수라, "각자 만들고 마지막에 합친다"는 방식은 큰 충돌 위험이 있었습니다.
- 기각된 대안: (A) 팀장이 ERD·디자인시스템을 전부 작성 — RFP가 데이터 모델링을 팀 전체 학습
  목표로 명시해서 기각. (B) 한 명이 AI로 풀스택 전체 생성 — 산출물 요건(팀원별 역할 분배, 스프린트
  회고록)이 성립하지 않고 단일 실패점이 생겨 기각. (C) `features/`에 실제 프로토타입 코드를 넣고
  나중에 `app/`로 통합 — 통합 시점에 한 번도 합쳐본 적 없는 코드를 합치는 "빅뱅 통합" 위험이 있어
  기각.
- 채택된 이유: 일 단위로 소규모 통합을 반복하면 충돌 크기가 작아지고, git이 미숙한 팀원도 그날그날
  해결할 수 있습니다.

**ADR-0006 (app/ 접근 권한, 2026-08-18) — ADR-0004의 원안을 재정의:**
- ADR-0004 원안은 "`features/`는 스펙·와이어프레임 전용, 코드 없음"이었습니다. ADR-0006이 이걸
  뒤집어 `features/{기능}/prototype/`을 "실제 구현 초안 코드 + Mock" 공간으로 재정의했습니다.
  **즉 지금 `features/*/prototype/`에 실제 코드(controller/service 등)가 있는 것은 위반이
  아니라 최신 결정(R12)을 따른 정상 상태입니다.** 오래된 문서나 사람의 기억이 ADR-0004 원안을
  기준으로 "features/에 코드가 있으면 안 된다"고 판단하면 이게 오탐입니다.
- `app/`을 팀원이 직접 건드리지 않고 팀장만 커밋하는 "완전 차단 방식"을 채택한 이유: 팀원의
  실수가 공유 코드베이스에 바로 반영되는 경로를 원천 차단하기 위해서입니다. 대신 팀장의 처리
  용량이 병목이 될 수 있다는 리스크를 안고 있습니다 (문서에도 명시된 미해결 리스크입니다).

**constitution.md 핵심 원칙 (판단 기준으로 사용):**
- 원칙 3: 같은 목적의 정보는 한 곳에 모은다 — 정본은 하나, 나머지는 링크로 참조.
- 원칙 5: 판단은 나누고 실행은 좁힌다 — `app/`·`docs/domain/`처럼 공유 자산의 최종 반영은
  팀장 한 사람에게 좁힌다.
- 원칙 6: 팀 규모(5인·22일)에 맞지 않는 복잡한 해결책을 먼저 고르지 않는다.
- 원칙 9: 확장은 "파일 1개 + 인덱스 1줄" 형태를 갖는다 — 공유 파일 본문을 직접 고치는 확장 방식은
  경고 신호다.

## 3. 판정 절차

R1부터 R14까지 순서대로, 각 규칙마다 아래 네 가지를 반드시 채우세요. 항목을 건너뛰지 마세요.

- **판정**: 준수 / 부분 준수 / 위반 중 하나
- **근거**: 위 §1의 규칙 원문 인용 + 실제로 열어서 확인한 파일·폴더 경로 (예: `features/reviews/spec.md` 존재 확인함, 0바이트)
- **경계 케이스 처리**: 규칙과 실제가 정확히 안 맞으면, §2 근거로 의도된 예외인지 실제 위반인지 먼저 판단하고 그 판단 이유를 적으세요
- **위반/부분 준수라면**: 무엇이 다른지, 어떻게 고치면 되는지 구체적인 다음 행동 1~2개

## 4. AGENTS.md에 없지만 신경 쓰이는 지점

아래 두 가지를 반드시 확인하고, 그 외에 스스로 발견한 지점이 있으면 1개 더 추가하세요. 이 항목들은
"규칙 위반"은 아니지만 구조적으로 짚어둘 가치가 있는 것들입니다.

1. `app/web/AGENTS.md`와 `users/AGENTS.md`를 실제로 열어 바이트 수를 확인하세요. 비어 있다면,
   이게 "이 폴더에는 별도 규칙이 없다"는 뜻인지 "아직 안 썼다"는 뜻인지 파일만 봐서는 구분할 수
   없습니다. 같은 계층의 다른 파일(`app/server/AGENTS.md`)과 비교했을 때 형평성이 맞는지도
   확인하세요.
2. `docs/decisions/0004-repo-structure.md`의 상태 필드를 확인하세요. 리포 전체 구조가 이 문서를
   전제로 운영되고 있는데, 문서 자체는 아직 "제안(팀 확정 전)" 상태로 남아 있을 수 있습니다.
   실제 상태와 문서상 상태가 어긋나 있는지 확인하세요.
3. (직접 발견) 위 두 가지 외에, 실제 폴더를 살펴보다가 "AGENTS.md엔 안 적혀 있는데 이상하다"
   싶은 지점이 있으면 여기 1개 추가하고 이유를 설명하세요.

### 설계 메모

- §1의 규칙은 루트 `AGENTS.md` 원문(2026-08-24 기준)을 그대로 인용했습니다 — `AGENTS.md`가
  갱신되면 이 프롬프트의 §1도 함께 갱신해야 합니다(그렇지 않으면 프롬프트 자체가 낡은 규칙으로
  검증하게 됩니다).
- §2의 "ADR-0004 원안을 ADR-0006이 재정의했다"는 내용은 실제로 자주 나올 오탐(false positive)
  지점이라 명시적으로 넣었습니다 — `features/`에 코드가 있다고 그 자체를 위반으로 판정하는
  실수를 막기 위한 것입니다.
- §4의 두 항목(빈 AGENTS.md, ADR-0004 상태 불일치)은 2026-08-24 기준 리포를 실제로 확인해
  찾아낸 현재진행형 이슈입니다 — 프롬프트 예시가 아니라 그 시점의 실제 상태였습니다. 시간이
  지나 해소됐다면 이 프롬프트를 실행하는 AI가 §4에서 "확인 결과 해소됨"으로 보고하면 됩니다.
- 이 프롬프트는 폴더·파일 구조만 검증합니다. 코드 품질, 테스트 통과 여부, ERD/PRD 내용 정합성은
  범위 밖입니다 (그건 `sdd-framework/feature-workflow.md`의 완료 조건과 `run.tsx` 검증의 몫입니다).
