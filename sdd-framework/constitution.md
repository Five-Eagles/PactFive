# PactFive Constitution

> 이 문서는 프로젝트 전체를 관통하는 원칙입니다. 개별 AGENTS.md·ADR·스펙 문서가 이 원칙과 충돌하면
> 이 문서를 기준으로 판단하고, 필요하면 이 문서 자체를 `change-requests/`로 개정합니다.

## 1. 사실·가정·의견을 구분한다
모든 결정 문서에서 확인된 사실(FACT), 검증되지 않은 가정(ASSUMPTION), 판단(OPINION)을 구분해
표기한다. 불확실한 내용을 사실처럼 쓰지 않는다.

## 2. 원칙과 구체 사례를 분리한다
문서는 원칙(형식·규칙)만 선언하고, 실제 값·목록·예시는 별도 문서에 둔다. 구현 단계에서는
예시·임시 선언을 그대로 반영하지 않고 참고만 한다.

## 3. 같은 목적의 정보는 한 곳에 모은다
같은 목적으로 쓰이는 정보를 여러 파일에 중복해서 두지 않는다. 정본은 하나만 두고, 나머지는
링크로 참조한다.

## 4. 통합은 매일, 작게 반복한다
막판에 한 번에 합치지 않는다. 매일 작은 단위로 통합해서 충돌의 크기를 줄인다.

## 5. 판단은 나누고, 실행은 좁힌다
설계·기준을 세우는 판단은 여러 사람(오너)에게 나누되, 공유 자산(`app/`, `docs/domain/`)에 대한
최종 반영은 병목이 되더라도 한 사람(팀장)에게 좁혀 충돌을 원천 차단한다.

## 6. 프로젝트 규모에 맞지 않는 복잡한 해결책을 먼저 고르지 않는다
구현 난이도·유지보수성·팀원 이해 가능성을 고려해, 지금 팀 규모(5인·22일)에 필요한 만큼만
설계한다.

## 7. AI는 협업자이지 최종 결정권자가 아니다
AI의 추천은 결정을 위한 근거 중 하나다. 최종 결정은 팀이 내리고, 근거·대안·이유를 기록한다.

## 8. 문서는 워크플로우에 붙여서 최신 상태를 유지한다
문서 최신화를 별도 의무로 두지 않는다. 이미 있는 작업 단계(통합, 회고 등)에 최신화 절차를
붙여서 실제로 지켜지게 한다.

## 9. 확장은 파일 1개 + 인덱스 1줄의 형태를 갖는다
새 결정·기능·템플릿을 추가할 때 여러 사람이 공유하는 파일의 본문을 고치는 방식이 아니라, 파일을
하나 추가하고 인덱스에 한 줄만 추가하는 방식을 기본으로 한다. 자세한 판단 절차는
`sdd-framework/evolution-rules.md` 참고.

## 10. 외부 벤더 의존은 인터페이스 뒤에 둔다
인증·결제·AI API 등 외부 벤더 SDK를 컨트롤러·서비스 코드에서 직접 호출하지 않는다. 벤더 교체
가능성이 있는 모든 접점은 인터페이스(포트)로 추상화하고, 벤더별 구현은 어댑터로 분리한다.
자세한 패턴·대상은 `docs/decisions/0009-external-vendor-interface-layer.md` 참고.
